## Freeze Summer 2026 before treating it as a course archive

This guide reviews Berkeley **CS 61C: Great Ideas in Computer Architecture, Summer 2026** rather than blending similarly named offerings into one resource pack. As of 2026-07-29, the official [course home](https://cs61c.org/su26/) describes a live offering. Its schedule plans 26 lecture slots, moving from C, number representation, and RISC-V through calling conventions, a single-cycle datapath, a 5-stage pipeline, caches, parallelism, and virtual memory. Later entries can still change. The page establishes what is currently posted or planned; it does not justify calling all 26 lectures a finalized recorded course.

The course addresses the interface question, “How does a program descend into a processor and memory hierarchy?” It makes a learner who already programs confront the C memory model, assembly, the ISA, datapath, and cache together. It does not train a full RTL microarchitect and does not replace an operating-systems course. The current schedule displays Labs 0–7, Homework 1–7, Discussions 1–12, Project 1 `snek`, Project 2 `CS61Classify`, and Project 3 `CS61CPU`, followed later by optional Lab 8 and Project 4. This is the live schedule inventory observed on 2026-07-29, not proof from the schedule alone of a complete required-assignment list. Actual requirements remain governed by the corresponding assignment, policy, and enrolled course systems.

## Three small diagnostics are more useful than “I have programmed”

First complete 3 checks that require no Berkeley account. For the first, write a small C program and explain its stack, heap, pointer arithmetic, undefined behavior, and one memory leak; then locate the defect with compiler warnings or a sanitizer. If you can only guess from printed output, review C, GDB, and basic Unix shell skills first. For the second, trace RISC-V containing a function call. Mark `sp`, `ra`, caller-saved and callee-saved registers, and the stack frame. If that fails, study instruction encoding and the calling convention before copying assembly.

For the third, use one `add`, one load, and one branch to draw the path through the PC, register file, ALU, memory, and control signals, then explain why a pipeline creates hazards. If Boolean logic, finite-state reasoning, or binary representation is weak, take an introductory digital-logic unit first. The official [course policies](https://cs61c.org/su26/policies/) list CS 61A and CS 61B or equivalents as prerequisites while also recognizing substantial C-based programming experience. Knowing Python syntax alone does not establish that threshold. These 3 checks are EEDIY placement diagnostics, not Berkeley enrollment permission or official assessments.

## The public spine is one C → RISC-V → CPU evidence chain

Do not treat notes, discussions, and labs as 3 parallel curricula. For each concept, read the current notes, attempt the matching discussion worksheet, and use only an officially published discussion solution for correction. Then enter the lab, where the concept becomes a tool and a test. At review time, the public Lab starter repository contains `lab00`–`lab07` and a tools directory. In an isolated local environment, preserve commits, build commands, and failing tests. The official [Lab 7](https://cs61c.org/su26/labs/lab07/) explicitly requires Hive rather than a local machine and gives performance expectations for Hive's SIMD/OpenMP environment. Similar local execution is not reproduction of the server configuration, timing data, or grader.

A useful record should align representations. For one matrix kernel, retain the C source, a corresponding RISC-V fragment, a cache-access trace, and an explanation of pipeline stalls or locality. For floating point, retain a bit-level example, its rounding error, and one boundary test. This prevents Project 2 from becoming “fill the supplied functions” and Project 3 from becoming “make the waveform move.”

This vertical alignment also localizes faults to language semantics, instruction semantics, or hardware implementation. When an array result is wrong, freeze the input and compare C and RISC-V memory accesses. When the instruction trace is correct but the processor output is wrong, inspect control signals, immediate generation, register writeback, and timing. Change one layer at a time and preserve the first divergence between expected and observed traces. Otherwise, simultaneous edits to source, assembly, and circuitry can produce an accidental pass without explaining why the fault disappeared.

## The 3 projects test different interfaces

The official [Project 1](https://cs61c.org/su26/projects/proj1/) is `snek`, emphasizing C, data structures, manual memory management, and testing, and it explicitly requires Hive rather than a local machine. A public starter can support reconstruction of the visible portion, but an independent record can claim only that it passes public and original tests—not the CS 61C grader or Hive environment. Keep source, original unit tests, a sanitizer or Valgrind-style report, and a bug log in a private repository that does not expose solutions.

The official [Project 2](https://cs61c.org/su26/projects/proj2/) decomposes a handwritten-digit classifier into RISC-V routines and explicitly requires a local machine. Establish small-function tests with `bash test.sh`, Venus, the calling-convention checker, and memcheck before checking calling conventions, memory layout, and integer arithmetic. The important artifact is not the final classification image. It is a trace showing that a wrong answer came from register preservation, stride, or address calculation. Public starters and tests cover only their visible contract; Gradescope hidden tests and staff feedback are not public.

The official [Project 3](https://cs61c.org/su26/projects/proj3/) asks learners to implement a processor in local Logisim that runs real RISC-V programs and explicitly says Hive is unnecessary. Preserve a control table, a single-cycle block diagram, per-component tests, instruction traces, and integration waveforms before entering the pipeline and cache material. Download scripts can obtain Venus and Logisim dependencies; they do not provide Berkeley Gradescope, the CBTF exam environment, or staff checkoffs. Public starters also do not authorize publishing completed solutions. The course policies cited above require solutions to remain invisible to others; keep independent completed work private and point to the upstream source.

## Public material is strong, but formal feedback has a hard boundary

The official policies describe a 300-point structure: labs 24, homework 36, each of 3 projects 30, quest 25, midterm 50, and final 75. Labs use Gradescope, homework uses PrairieLearn, and exams and current recordings also depend on Berkeley systems. An outside learner can use notes, discussion worksheets and published solutions, lab and project specifications, and starters. They cannot claim access to bCourses recordings, an instructional account, the course PrairieLearn instance, Gradescope hidden tests, or staff office hours. Do not borrow a Berkeley account or present an inaccessible grader as an independent feedback loop.

The policy expressly prohibits receiving, publishing, or seeking unauthorized solutions and requires private project repositories. Independent study should likewise use only solutions that the course itself made public. Do not fill gaps from student repositories, chat logs, or scraping sites. For homework and projects without official answers, use a small oracle, property tests, compiler or simulator traces, course-published discussion examples, and peer review that does not exchange answers. Passing one test proves only that input; it does not establish hidden-test coverage.

## Dependency, not a generic calendar, determines the order

The first segment stops at C and representation: complete Lab 0–2-type work, a personal memory-error dossier, and a reconstruction of the reasoning—not merely the result—behind at least one published discussion solution. The second segment enters RISC-V: finish Project 1 before instruction encoding, calling conventions, and Project 2. If register and stack failures remain recurrent, pause before the datapath. Only the third segment enters digital implementation: use Project 3 to align ISA traces with control signals, then study pipelines, caches, SIMD/OpenMP, and virtual memory. Because the course is still live, record the retrieval date and upstream commit when material changes; do not silently splice files from different terms.

Completion evidence should include the first attempts and remediation for all 3 diagnostics; a public/account-only/not-attempted table for Labs 0–7, Homework 1–7, and Discussions 1–12 as displayed on the 2026-07-29 schedule; private commit histories, public-test reports, traces or waveforms, and postmortems for Projects 1–3; and an access ledger stating that Hive, bCourses, PrairieLearn, Gradescope, CBTF, and Berkeley accounts were not reproduced. This is EEDIY's tracking scope for the live page, not an official required inventory inferred from a calendar. Optional Lab 8, Project 4, and an independently invented CPU are not promoted into official tasks.

## When to hand off to Cornell ECE 4750

This comparison is frozen to Cornell ECE 4750 **Fall 2025**. The official handouts index dates its syllabus and lecture/lab PDFs to 2025, while the [Lab Assignment Logistics](https://www.csl.cornell.edu/courses/ece4750/handouts/ece4750-lab-logistics.pdf) specifies Verilog RTL, Python/`pytest` verification, cycle and performance evaluation, and four cumulative labs. The Fall 2026 landing page still says “under construction” as of 2026-07-29, so it is not treated as a finalized replacement.

Public Fall 2025 handouts are readable, but the original labs are not independently executable from those PDFs. The official flow logs into Cornell `ecelinux`, sources the course environment, and clones a private `cornell-ece4750/lab-groupXX` repository created for each group. Instructor tests, GitHub Actions, feedback, and later code merges remain inside that private chain. An outside learner may study the briefs and make a clearly labeled port in a lawfully available Verilog/Python environment, but cannot claim completion of the original ECE 4750 labs.

ECE 4750 goes further into processor, cache, and multicore microarchitecture, RTL verification, and cycle-level reasoning. CS 61C is the stronger first broad spine across C, RISC-V, datapaths, caches, and systems programming. If a pointer defect cannot yet be traced into a memory trace, finish the public CS 61C scope first. If ISA tests can already be connected to pipeline hazards and the missing Cornell private environment will be recorded rather than hidden, move to the RTL training defined by the Fall 2025 handouts.
