## Bits, Signals, and Packets Must Form One Causal Chain

The MIT [6.02 Fall 2012 syllabus](https://ocw.mit.edu/courses/6-02-introduction-to-eecs-ii-digital-communication-systems-fall-2012/pages/syllabus/)
organizes digital communication across 3 layers. Bits covers entropy,
Huffman/LZW, linear block codes, convolutional codes, and Viterbi decoding.
Signals covers Gaussian noise, BER, LTI channels, convolution, Fourier
methods, filters, and modulation/demodulation. Packets covers TDMA/Aloha/
carrier sense, queues, Little’s law, routing, and reliable transport. The
course does not merely sample information theory, signals, and networking. It
asks how redundancy buys reliability and how sharing buys efficiency.

That breadth also determines the final explanation. The PS6 physical-channel
result constrains the usable packet rate, while PS9 window efficiency depends
on link delay. By the end, trace how noise, ISI, and clock recovery change
throughput and latency layer by layer. Separate reports that say “the codec
passes, the eye is plotted, routing runs” do not yet show the course’s central
cross-layer reasoning.
Trace one failed transmission backward: distortion changes sample decisions;
errors change retransmissions and arrival spacing; queues and RTT then decide
whether the window fills the link. Name each layer’s input, output, and units
instead of reusing one BER plot.

## Use a Self-Check to Choose What to Review, Not Whether to Learn

The official prerequisites are 18.03 and 6.01, with Python at the 6.00/6.01
level. EEDIY separates them into 3 editorial diagnostics. In probability, try
conditional probability, expectation, and a Gaussian tail. In signals, solve
a first-order LTI difference equation, perform convolution, and explain a
complex exponential. In programming, implement a queue, numerical loop, and
unit test without changing a function contract. This is not an MIT score
threshold, and one miss does not mean “leave the course.” The specific failed
action only chooses whether to review probability, signals, or Python first.
Convert self-check failures into first-week work: stalled probability becomes
hand calculations with conditioning; stalled convolution becomes term-by-term
sums on short sequences; stalled interface tests become pure functions on
minimal inputs. Review follows observed errors, not course labels or
confidence.

The original sequence has 24 lectures: Lectures 1–7 are Bits, 8–16 Signals,
and 17–24 Packets, with 1 quiz after each segment. *Bits, Signals, and Packets*
has 19 chapters. The 11
[Tutorials with solutions](https://ocw.mit.edu/courses/6-02-introduction-to-eecs-ii-digital-communication-systems-fall-2012/pages/tutorials/)
lead into end-of-chapter work, whose solutions are not public. A useful rhythm
every 2–3 lectures is “read the chapter, attempt the Tutorial, correct it, then
enter the PS,” rather than watching every video before writing code.

## Map PS, Legacy Interface, Python 3 Interface, and Reference Oracle

The 9 problem sets are arranged 3+3+3. The official
[Assignments index](https://ocw.mit.edu/courses/6-02-introduction-to-eecs-ii-digital-communication-systems-fall-2012/pages/assignments/)
lists the PDF and supporting files for PS1–PS9 individually; the table keeps
the same clear row names, so every assignment is one click away through that
index. Every Python 3 contract, fixture, and oracle below is an EEDIY testing
design for independent study, not code distributed by MIT. The legacy column
follows only the call conventions that the handout and official ZIP actually
expose; it does not pretend to know the internals of missing modules.

| PS | Problem | Legacy-environment interface | EEDIY Python 3 interface | Small fixture | Reference oracle and comparison |
| --- | --- | --- | --- | --- | --- |
| PS1 | Huffman, LZW, and compression | Python 2 task entry points and `.zl` streams | `encode(input)->bits`, `decode(bits)->input`, plus code table | 4–8 symbols, a hand-written frequency table, and short string | Hand-calculate tree/table/bitstream; round-trip and bit count are exact |
| PS2 | Linear block code and syndrome | Provider encoder/decoder module | Pure bit-array encode/decode, also returning syndrome | A small \(G,H\) and 0/1-bit error | Enumerate every codeword and error; bits and syndrome are exact |
| PS3 | Convolutional code and Viterbi | Provider trellis task | Decode returns bits, state path, and path-metric trace | A 2–4-state trellis and short received sequence | Hand-calculate trellis; declare tie policy first, then require exact path and metric |
| PS4–6 | Signaling, clock recovery, noise, ISI, eye, filtering, and modulation | Audiocom sample-array/audio-device/GUI path | Pure array transforms + WAV/file adapter; live audio isolated separately | Impulse, short waveform, fixed lag/noise seed, and small WAV | Compare only when an isolated-VM reference trace exists; discrete fields exact, float tolerance derived from dtype, trace, and normalization |
| PS7 | TDMA, Aloha, and carrier sense | Event simulator and statistics output | Seeded event stream in, transmission/collision trace out | A few hand-written arrivals and fixed backoff | Schedule by hand; event count, collision, and success are exact |
| PS8 | Distance-vector and link-state routing | Topology/update simulator | Graph + ordered update/event stream → routes/costs | A 4-node graph and 1 link failure | Hand-calculate shortest path and update sequence; fix tie policy for equal cost |
| PS9 | Reliable transport and sliding window | Packet/ACK/timer callbacks | Deterministic packet/ACK/loss/delay events → sender/receiver state trace | A small window, fixed delay, and 1 loss | Hand-write state transitions; sequence/ACK/timer exact, throughput calculated from the deterministic timeline |

Begin with hand-calculable cases, not a comparison of large simulation plots.
Exact discrete results need no “close enough” tolerance. Beside every floating
fixture, record units, dtype, normalization, reference source, and the
derivation of its tolerance. Interface compatibility is not algorithmic
equivalence; complexity, failed inputs, and tie-breaking remain part of the
explanation.
Oracle independence is central. Expected output generated by the code under
test only repeats its mistakes. Hand-derived codewords, schedules, and routes
separate expectation from implementation. At larger scales, compose checked
modules and test conservation laws, bounds, and extremes rather than accepting
plausible plots.

## Audiocom Has Verifiable Distribution Provenance but Uncertain Behavior

PS4 sends a file from speaker to microphone. PS5 studies step/impulse response,
ISI, and the eye diagram. PS6 handles a preamble, unknown lag, noise, channel
distortion, and concurrent transmission. The Assignments index says the
Audiocom supporting ZIP contains 17 `.py` and 4 `.pyc` files. The MIT OCW
[Audiocom ZIP resource](https://ocw.mit.edu/courses/6-02-introduction-to-eecs-ii-digital-communication-systems-fall-2012/resources/audiocom/)
separately establishes the official distribution source. Those facts should
not be collapsed into “the resource page lists the counts.” The MIT provenance
of the distributed files is not ambiguous. What is missing is published source
for those 4 `.pyc` files and a reproducible build chain that recreates them
from source.

This distinction controls claims about a Python 3 rewrite. If the official ZIP
runs in an offline, isolated, disposable Python 2 VM and produces reference
traces for fixed inputs, compare a modern implementation on the same fixtures
while recording environment, file hash, sample rate, dtype, random seed, and
tolerance. If the VM cannot generate reference traces, reimplement only from
the public assignment description and state “behavioral equivalence
unverified.” Do not call it a line-by-line port or equivalent replacement.
A reference trace proves agreement only for its chosen input, not every
hidden-module behavior. Add boundary cases: no signal, very short records,
abnormal sample rates, and deterministic noise. Mark where legacy output fails
or is undefined; those gaps say more than a blanket compatibility claim.

The official [Software page](https://ocw.mit.edu/courses/6-02-introduction-to-eecs-ii-digital-communication-systems-fall-2012/pages/syllabus/software/)
lists Python 2.7.x, wxPython 2.8 Unicode, numpy 1.5.1, and matplotlib 1.0.1.
Its Mac OS X 10.6 directions require the then-current 32-bit packages. This
records the Fall 2012 environment; it is not a current installation tutorial.
Even with trustworthy ZIP provenance, the unmaintained interpreter, GUI, and
binary belong only in an isolated VM, not a daily networked environment.

## Pass WAV before Enabling a Speaker

Make the Python 3 implementation of PS4–6 work first through array/WAV/file
loopback. Fix sample rate, seed, amplitude limit, and input file, then test
transmitter, channel, synchronizer, and receiver separately. Only after that
path is stable should an existing computer speaker/microphone become an
optional adapter. The course requires no dedicated sound interface and gives
no current device budget.

For real audio: use no headphones; mute before rewiring, selecting a device, or
changing routing; add a software amplitude limiter/clip and begin with low
operating-system and hardware volume; keep the speaker away from microphone
and ears; stop playback and mute immediately on feedback squeal, unexpected
loudness, or clipping. Do not add an RF transmitter for “realism.” It is not
required by the assignment and introduces spectrum and RF-safety concerns.
Record device name, channel map, system gain, sample-rate conversion, and
buffer length. After changing computers, send the same WAV through the file
path to isolate software differences before enabling speakers to test the
sound card, room, and feedback. Otherwise hardware and algorithm changes are
confounded.

## Recover Feedback with Tutorials, Oral Questions, and an End-to-End Account

The 9 formal problem sets have no public official solutions. The enrolled
course also used 6 TA check-off interviews of 15–20 minutes, while the 3
quizzes have no public solutions. Use the 11 Tutorial solutions for basic
checking and keep each quiz blind. After Bits, Signals, and Packets, ask
another person to spend 15–20 minutes probing when LZW expands, how Viterbi
state count grows, why an eye closes, how distance vector counts to infinity,
and why a window is delay-limited. When the explanation fails, return to the
model and small fixture instead of hiding it under more comments.
Oral checks are not definition recall. Change a probability, noise level, link
cost, or window size; require a directional prediction before running. If
result and prediction disagree, follow state and units to the first divergence.
This recovers the check-off’s purpose and catches “green tests, no
explanation.”

One final EEDIY integration exercise can compress a message, add a convolutional
code, pass it through a baseband channel with noise, ISI, and timing offset,
recover packets, and reroute a multi-node network after a link failure. Report
useful throughput, BER, delay, and overhead as parameters change, then explain
the PS6 packet-rate → queue/load → PS9 window/delay causality. This is not a
new MIT 6.02 project and does not replace dedicated courses in stochastic
processes, DSP, or computer networks. It checks only whether Bits, Signals, and
Packets truly became one system.
