## This is a runnable author companion, not a currently delivered CDS 101

Caltech's [author-maintained home](https://fbswiki.org/wiki/index.php/FBS) organizes material around the 2nd edition of Åström and Murray's *Feedback Systems: An Introduction for Scientists and Engineers*. The official page supplies the complete text dated 2020-07-24 and a separate page for every chapter. A chapter page lists teaching material, additional exercises, FAQs, and plotting code when those resources exist; some fields explicitly say `None available`. It is therefore inaccurate to say that every chapter has extra examples and exercises. The 15 chapters move from feedback principles, modeling, and dynamic behavior through state and output feedback, transfer functions, PID, frequency-domain design, robust performance, fundamental limits, and system architecture. This is a book and companion site; it must not be represented as the syllabus, deadlines, or classroom support of a current CDS 101/CDS 110 offering.

That distinction changes how one studies it. Permission to read the text gives an outside learner no instructor manual, grading, TA, or grader. “Examples” and “exercises” on the site are also not scheduled assessments in a live course. The right learner already knows differential equations, linear algebra, and basic Python and wants to connect physical modeling, feedback design, and robustness across disciplines. Someone who first needs many linear-algebra calculations, or a full item-by-item answer loop, should pay close attention to the EE 263 comparison below.

## Model: first test the move from physical prose to a state equation

Complete 3 diagnostics before opening the main sequence. First, define the input, state, output, disturbance, and parameters for cruise control or a DC motor, write a nonlinear differential equation, and check dimensions. Second, compute a Jacobian linearization at an equilibrium and explain its eigenvalues and time constants. Third, predict both step response and Bode magnitude and phase for a first- or second-order model, explaining when the representations give the same conclusion. A failure on item 1 calls for free-body diagrams and conservation laws; a failure on item 2 calls for an ODE and linear algebra review; a failure on item 3 calls for linear systems and complex frequency.

After passing the diagnostics, do not advance at one chapter per day. Read Chapters 1–4 first and use the static and dynamic examples on [Feedback Principles](https://fbswiki.org/wiki/index.php/Feedback_Principles) as a modeling audit. For every block, state signal direction, units, equilibrium, disturbance injection point, and measurable output. The page uses examples such as cruise control to explain disturbance attenuation, tracking, parameter robustness, PI, 2-degree-of-freedom design, and positive feedback. They are best used to ask why feedback is needed, not to memorize controller names.

The first artifact is a model ledger. For one plant, retain the nonlinear model, linearized state-space model, transfer function, and simulation interface, and state what each simplification discarded. If a parameter change moves the equilibrium but the learner keeps comparing linear responses around the old operating point, return to the model. Controller tuning must not hide a modeling error.

The ledger must also distinguish “physically unmeasurable” from “not instrumented in the current implementation.” The first changes observability and control structure; the second may only be an implementation constraint. For every disturbance, mark whether it enters at the plant input, state equation, or measurement channel, because those placements define different sensitivity questions. These annotations turn a block diagram into an interface contract for later design decisions.

## Analysis: make equations, plots, and code challenge one another

Chapters 5–10 connect dynamic behavior, linear systems, state and output feedback, and frequency response. For each pole or zero claim, perform a 3-way check: calculate a characteristic equation or eigenvalue; generate a step, Bode, or Nyquist plot; and test the sign and scale in a limiting case. A smooth curve is not proof. Record the initial condition, sampling grid, units, and whether saturation was omitted.

The public official [Python repository](https://github.com/murrayrm/fbs2e-python) uses a BSD-3-Clause license, contains 2nd-edition figure and example scripts, and was updated on 2024-11-16 for `python-control 0.10.1`. Pin `python-control 0.10.1`, the Python environment, and an upstream commit. Reproduce one provider figure appropriate to the current chapter, then vary 1 physical parameter, 1 disturbance, and 1 measurement-noise setting. Explain which analytical conclusion survives and which fails because of the model or numerical conditions. `run_all.sh` and the figure scripts are executable evidence, not an exercise grader.

The exit test for analysis is not “every script ran.” It is the ability to return from a curve to a mechanism. When resonance rises, distinguish damping ratio, an unmodeled mode, and numerical resolution. Connect Nyquist encirclement of the open loop to closed-loop stability rather than reading a software margin alone. If the same phenomenon cannot be explained in 2 representations, remain in Chapters 5–10 instead of entering a controller cookbook.

## Design: write constraints before choosing PID or state feedback

Chapters 7–12 turn analysis into design. Begin with a performance contract for the running example: reference tracking, disturbance band, allowable overshoot, control effort, sensor noise, and actuator limits. Complete at least 2 routes, one using state or output feedback and the other using PID or loop shaping. For each, retain plant assumptions, controller equations, closed-loop poles or loop shape, simulation cases, and a failure case. Similar nominal step responses do not establish similar implementation cost or robustness.

EEDIY recommends one controller-comparison notebook: apply identical disturbances and saturation to 2 controllers on the same model, then write a 1-page design memo. This is not an official Caltech assignment and is not evidence of completing CDS 101/CDS 110. Text exercises can supply questions, but where no public answer exists, correct them with dimensional checks, special cases, independent simulation, and peer derivation that does not exchange answers. Do not turn a personal notebook into a supposed “official solution.”

The common sticking point is not calculating one gain; it is translating an objective into a measurable specification. If the method is repeated parameter adjustment until a plot looks good, return to the contract and mark which plot or calculation covers the sensitivity function, complementary sensitivity, input constraints, and uncertainty. An uncovered constraint belongs in an open-risk list, not under an unsupported claim of stability.

## Robustness: move model mismatch into the center of design

Chapters 13–15 treat robust performance, fundamental limits, and architecture. The official Robust Performance page connects uncertainty, Nyquist robust stability, and \(H_\infty\)-style performance; it should not become optional last-page reading. Build a 3-layer envelope for the running example: a parameter interval, unmodeled high-frequency dynamics, and sensor noise or actuator saturation. Sweep the nominal controller and record the worst case, failure mechanism, and metrics that cannot be satisfied together.

Then examine how a nonminimum-phase zero, time delay, Bode integral, gain crossover, and nonlinear limits constrain “add more gain.” The final architecture drawing should assign responsibilities to sensor, controller, actuator, reference shaping, and safety interlock. A safety interlock here is a system-architecture concept; it does not authorize connecting the simulation to a vehicle, person, industrial device, or high-energy actuator. Physical work requires separate qualified supervision, rated hardware, and a risk review. This guide defaults to simulation.

The robustness artifact is a failure map rather than the best nominal plot. For each perturbation, record the expected mechanism, observed metric, accept or reject threshold, and corrective design. If every test succeeds, suspect that the test range is too narrow. Preserve at least 1 explained failure point to show that the envelope is doing real work.

When explaining a failure, separate a structural limit from inadequate tuning. A right-half-plane zero, delay, or actuator saturation cannot be removed by increasing bandwidth. An anomaly caused by a unit error, shifted operating point, or numerical step size should not be relabeled as a control-theory limit. Only after separating those cases can the learner decide whether to return to the model, change the architecture, or redesign the controller.

## Put the solution boundary and completion criteria on the same page

Caltech's official historical [solutions-manual notice](https://www.cds.caltech.edu/~murray/books/AM05/wiki/Solutions_manual.html) states that the manual is restricted to instructors, is not distributed online to students, and must not be posted publicly. The notice comes from the author-maintained Feedback Systems site. It establishes an access boundary; it is not a clue for finding a mirror. EEDIY does not link copies indexed elsewhere or use restricted answers on the premise that independent study is exempt. The public layer has no course grader, TA checkoff, or complete exercise-answer loop.

A reviewable completion package should contain all 3 prerequisite diagnostics; 1 plant carried through model→analysis→design→robustness; an environment pinned to `python-control 0.10.1` and an upstream commit; a provider-figure reproduction and perturbation report; 2 controller routes; a failure map; and a Chapter 1–15 index marking reading, exercise, and status. Mark unfinished exercises as unfinished rather than substituting a count of generated plots for the quality of derivations.

Stanford now needs to be split into 3 resources rather than collapsed under “EE 263.” Starting in Fall 2025, the current [EE 263](https://ee263.stanford.edu/) became **Matrix Methods: Singular Value Decomposition**, concentrating on range and null spaces, QR, least squares, eigenvalues, SVD, Gaussian distributions, and MMSE. Linear dynamical systems moved to [EE 363](https://ee363.stanford.edu/), which covers state space, matrix exponentials, stability, reachability, observability, LQR, and the Kalman filter. Canvas, Gradescope, and current-run recordings for those live courses are not anonymous outside feedback services.

A separately labeled [historical EE 263 archive](https://ee263.stanford.edu/archive/) preserves the 2008 **Introduction to Linear Dynamical Systems** version, including public videos, slides, support notes, and homework, and combines applied linear algebra with LDS in one course. Choose current EE 263 for matrix methods; EE 363 when the matrix foundation is ready and LDS is the target; the historical archive for an open, year-stamped matrix/LDS self-study package; and this Feedback Systems companion for the longer path from physical modeling through feedback design, limits, and robustness.

A report should name course ID 073, book version, chapter, code commit, and reproducible output, and must not submit the manual, restricted answers, or claim current Caltech or Stanford teaching support. This remains an R0 desktop review.
