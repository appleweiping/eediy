## 一门很紧的软硬件接口课程

Stanford [EE180 Course Home](https://web.stanford.edu/class/ee180/) 的 Winter 2026
页面用 18 讲从 assembly 与 hardware/software interface 走到 processor/pipeline、
cache/memory、virtual memory、OS support、I/O 和 accelerator。官方
[Course Information PDF](https://web.stanford.edu/class/ee180/ee180info.pdf) 与首页有少量
行政日期冲突，自学只需固定这套 topic/reading sequence。它适合已经会 C/C++、assembly、
基本 RTL 和 performance arithmetic，想从 workload 追到系统瓶颈的人。

## 每讲都留一条 trace

ISA 段追 registers 和 memory；pipeline 段逐 cycle 画 forward、stall、flush；memory 段拆
tag/index/offset 并算 AMAT；accelerator/I/O 段写 data movement、latency、throughput 和
energy assumption。只读商业教材与 slides，很容易把体系结构学成术语辨认。

页面列 Homework 1–3 与 Lab 1–4 的节奏；Lab 2 的分组人数尚未公布，Labs 3 和 4 要求两人，Lab 1 建议配对。assignment buttons 和许多 slides 进入需要
SUNet 的 [Canvas](https://canvas.stanford.edu/courses/217278)。校外拿不到完整 handout、
starter、FPGA allocation、Gradescope、solution 和 TA feedback，不能根据 “Lab 2” 名字
猜任务。以下 4 项是编辑补充，均为非官方项目：software optimization、pipelined processor、
cache experiment、accelerator/I/O integration；没有 FPGA 时标 pre-board。

## 性能评估

EE180 最值得练的是看出瓶颈有没有真的移动。对同一个 workload，把 instruction mix、IPC/CPI、
clock、cache miss、memory stall、data-movement time、accelerator utilization、energy proxy
与 total runtime 放在一起看；先确认优化前后输出相同，再改变 working set、memory latency 或
input size，寻找 break-even point 和失败范围。一张 speedup 图只能说明局部变快，解释不了代价
转移到了 cache、memory 还是 host interface。

一项失败优化往往比顺利的案例更有意思：计算部分可能更快，端到端却被 data movement、
working-set spill 或 synchronization 拖慢。用相同输入和固定测量窗口比较 baseline 与
optimized version，并改变 problem size 和 locality，直到能说明瓶颈转移的条件；几百分点的
差异若没有 counter 采样区间、warm-up、重复次数和噪声范围，很可能只是测量抖动。无法解释的
异常通常正好暴露了模型遗漏。学完后可以自拟一组覆盖
pipeline、cache/VM 与 accelerator trade-off 的综合题，用来串起这些判断，但它并非 Stanford
成绩。
