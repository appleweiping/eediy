## 先把 Summer 2026 冻结成一个可核验版本

本页审读的是 Berkeley **CS 61C: Great Ideas in Computer Architecture, Summer 2026**，不是把历年同名课程混成一套资源包。官方[课程主页](https://cs61c.org/su26/)在 2026-07-29 仍处于开课过程中：日程表计划了 26 个 lecture slot，主线从 C、数值表示和 RISC-V 延伸到 calling convention、single-cycle datapath、5-stage pipeline、cache、parallelism 与 virtual memory；后半段尚可能调整。因此，页面可以证明当前已经发布和计划发布的材料，却不能把 26 讲写成一套已经封版的录播课。

这门课解决的是“程序怎样一路落到处理器和存储层次”这个接口问题。它让写过高级语言的人同时碰 C memory model、assembly、ISA、datapath 与 cache，但不会把你训练成 RTL 微架构设计者，也不会替代 operating systems。当前日程显示 Lab 0–7、Homework 1–7、Discussion 1–12，以及 Project 1 `snek`、Project 2 `CS61Classify`、Project 3 `CS61CPU`；后面还显示 optional Lab 8 和 Project 4。这是 2026-07-29 的 live schedule inventory，不是由日程表本身证明的“全部官方必做清单”；实际要求仍以对应 assignment、policy 和注册后的课程系统为准。

## 三次小诊断，比“学过编程”更有用

开始前先独立完成 3 个不依赖 Berkeley 账户的检查。第一，写一个小 C 程序，解释 stack、heap、pointer arithmetic、undefined behavior 和一次 memory leak，并能用 compiler warning 或 sanitizer 定位错误。若只能凭输出猜测，先补 C、GDB 和基本 Unix shell。第二，手算一段含 function call 的 RISC-V：标出 `sp`、`ra`、caller-saved/callee-saved register 与 stack frame；不会时先读 ISA encoding 与 calling convention，而不是直接抄 assembly。

第三，从一条 `add`、一条 load 和一条 branch 出发，画出 PC、register file、ALU、memory 与 control signal 的数据流，并说明为什么 pipeline 会产生 hazard。若 Boolean logic、finite-state reasoning 或二进制表示尚不稳，先做数字逻辑入门。CS 61C 的官方[课程政策](https://cs61c.org/su26/policies/)把 CS 61A 与 CS 61B 或同等经验列为先修，同时接受扎实的 C-based programming experience；这不是只会 Python 语法就自然满足的门槛。以上 3 项是 EEDIY 的开课诊断，不是 Berkeley 的选课许可或官方测验。

## 公共主线是一条 C → RISC-V → CPU 的证据链

不要把 notes、discussion、lab 当成 3 套平行材料。每遇到一个概念，先读当前 notes，再做同主题 discussion worksheet；只有官方已经公开的 discussion solution 可用于订正。随后进入 lab，把概念落实到工具和测试。公开 Lab starter repository 在本次审读时包含 `lab00`–`lab07` 与工具目录，可在自己的隔离环境中保留 commit、编译命令和失败测试。但官方[Lab 7](https://cs61c.org/su26/labs/lab07/)明确要求在 Hive 而非本地机器完成，并以 Hive 支持的 SIMD/OpenMP 环境给出性能参照；校外机器能运行相似代码，不等于复现了课程服务器的配置、时间数据或 grader。

一份好的学习记录应让各个表示层彼此对得上。例如，同一个矩阵内核至少留下 C 源程序、对应的 RISC-V 指令片段、缓存访问轨迹（cache-access trace），以及对流水线停顿或数据局部性的解释。浮点数部分则保留逐位展开的例子、舍入误差分析与一次边界测试。这样，Project 2 的分类器不会退化成“把给定函数填完”，Project 3 的 CPU 也不会退化成“让波形看起来会动”。

这种纵向对照还有一个用途：定位错误究竟属于语言语义、指令语义还是硬件实现。数组结果错误时，先固定输入并比较 C 与 RISC-V 的内存访问；指令级结果正确而处理器输出错误时，再查控制信号、立即数生成、寄存器写回和时序。每次只改变一个层级，并在记录里保留预期 trace 与实际 trace 的第一个分歧点。否则，调试容易变成同时改源程序、汇编和电路，最后虽偶然通过测试，却无法说明故障为何消失。

## 3 个项目分别检查不同接口

官方[Project 1](https://cs61c.org/su26/projects/proj1/)对应 `snek`，重点是 C、data structure、manual memory management 与测试，并明确要求在 Hive 而非本地机器完成。公开 starter 可以支持校外重建可见部分，但独立学习记录只能写“通过公开测试/自写测试”，不能写“通过 CS 61C grader”或“复现 Hive”。source、自写 unit test、sanitizer/Valgrind 类报告和 bug log 应保存在不公开解答的 private repository 中。

官方[Project 2](https://cs61c.org/su26/projects/proj2/)把 handwritten-digit classifier 拆成 RISC-V routines，并明确要求在本地机器完成。先用 `bash test.sh`、Venus、calling-convention checker 与 memcheck 建立小函数测试，再检查 calling convention、memory layout 与整数运算。最有价值的不是最后一张分类结果，而是能把某次 wrong answer 追到 register preservation、stride 或 address calculation。公开 starter/test 只能覆盖可见 contract；Gradescope hidden tests 与 staff feedback不在公开层。

官方[Project 3](https://cs61c.org/su26/projects/proj3/)要求在本地机器的 Logisim 中实现能运行真实 RISC-V 程序的处理器，并特别说明不需要 Hive。建议依次保存 control table、single-cycle block diagram、每个 component test、instruction trace 和 integration waveform，再进入 pipeline/cache 讨论。下载脚本能够取得 Venus/Logisim 依赖，不会给你 Berkeley 的 Gradescope、CBTF exam environment 或 staff checkoff。公开 starter 可读也不自动授予重新发布成品的许可；前文所引课程政策要求解答不对外可见，独立学习成品同样保持 private，并链接上游。
