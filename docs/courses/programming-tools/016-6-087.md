## 先看清三周课程的速度

[MIT 6.087 Practical Programming in C, January IAP 2010](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/) 是一门密集短课，不是零基础编程导论。三周内每周有 5 次、每次 1.5 小时的讲课，以及 1 次、每次 3 小时的实验。官方先修表述是已经具有 6.00、1.00、6.01 或同等课程带来的基本编程能力；此前既不要求、也不希望已有 C 经验。换句话说，它会教 C 的具体机制，却不会慢慢解释什么是循环、函数分解或调试。

开始前直接取 [Assignments](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/pages/assignments/) 的 Assignment 1 做一次原生检查：不求背下所有语法，但应能在命令行编译一个多函数程序，读懂编译器的行号，并把失败缩小到输入、控制流或数据表示。若连“写代码—编译—运行—观察退出状态”的循环都无法独立完成，先补一门普通编程入门课；不要指望三周课程同时补齐算法思维和 C 的内存模型。

## 十四讲应该怎样读

[Lecture Notes](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/pages/lecture-notes/) 公开 14 组幻灯片，没有课堂录像。前半段依次处理编译与调试、类型、控制流和 I/O、指针、结构体/联合体/位域、动态分配、链表与树、二级指针、数组、栈和队列；后半段进入函数指针、哈希表、库、B 树、优先队列、标准库、malloc 实现与 Valgrind、垃圾回收、线程、socket、异步 I/O 和 Linux IPC。这里的广度大于三周内能沉淀的深度，不能把“看过第 14 讲”当作掌握并发和网络编程。

一个有效的读法是让每讲至少留下一个可执行的微例子，并能说明对象的生存期、所有权与失败路径。讲到指针时画出地址和指向关系；讲到动态分配时测试正常释放与错误路径；讲到线程和 socket 时区分 API 调用成功、部分完成和失败。课程使用 Athena UNIX 环境，但 OCW 不向外部学习者提供 Athena。今天可以在本地 Linux、WSL 或容器中用 GCC/Clang、make、gdb/lldb、Valgrind，或用 AddressSanitizer/UndefinedBehaviorSanitizer 补充检查；这是现代迁移方案，不是 2010 MIT 的原始环境要求。

## 作业不是八份，6a 与 6b 是同一组的两半

官方说明称前两周共有 7 份每日作业，而页面表格有 Assignment 1、2、3、4、5、6a、6b、7 共 8 行。应把 6a 与 6b 视为 Assignment 6 的两个部分，而不是改写成 8 份作业。公开表中每组都提供可用于核对的解答或示例，Assignment 7 的解答是 ZIP。自学时先只下载题目与所需数据；通过本地测试并完成一次代码复查后，再打开官方解答比较接口、错误处理和数据结构选择。

编译基线可统一为当前编译器的 C 标准模式、全部常用警告并把警告视为错误，但不要虚构一个 MIT 当年的命令行。每份作业至少运行正常输入、空输入或最小规模、边界长度、非法输入和资源失败中适用的几类。除了程序输出，还记录退出状态、标准错误、泄漏/越界报告，以及哪个测试真正覆盖了某条分支。

## 两次实验构成一条连续的测试线

### Lab 1：Game of Life 有公开 starter 和 solution

[Labs](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/pages/labs/) 为 Lab 1 同时提供 starter ZIP 与 solution ZIP。说明书要求读取世界状态并推进 Conway’s Game of Life；官方核对包括把 `NUM_GENERATIONS` 设为 50，对 `glider.txt` 和 `sship.txt` 运行，检查写出的 `world.txt`，并提交一页报告。外部学习者应保留输入文件、编译命令、50 代运行输出以及与参考结果的差异。看 solution 前先通过这些测试，才能让公开答案发挥复盘价值。

这次实验不只检查二维数组。应额外验证边界格、全死世界、稳定结构和振荡结构，说明边界采用了什么规则，并在内存检查工具下运行。若改变了 starter 的接口或边界语义，报告中必须明说；否则即使屏幕图案相似，也不能与官方任务直接比较。

### Lab 2：Huffman 没有公开 solution

Lab 2 公开 starter ZIP，却没有解答列。课堂内的 decoder 应把给定码流还原成内容为 `abbacafebad` 的 `decoded.txt`；后续 project encoder 必须生成指定代码，并让大文件解码后的 `decoded.txt` 与 `book.txt` 按字节一致。这里最有价值的结课证据不是压缩率截图，而是可重复命令：编码、解码、用 `cmp` 比较文件、显示退出状态，并在空文件、单符号文件、含全部字节值的文件和被截断码流上说明行为。

Lab 2 的无解答状态必须保留。可以通过 round-trip、独立小样例、树的前缀性质和内存工具增加把握，但不要把自己写的实现称为官方参考实现。原课实验由两人合作并由工作人员签字，站外学习失去的正是现场提问、签字与配对调试，不应由一张“已完成”勾选框掩盖。

## Final Project 要运行得起来，而不只是引用库

[Final Project brief](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/9796fe2dda5404aa9d14a49081b842d8_MIT6_087IAP10_project.pdf) 要求使用一个或多个开源库，提交一页 proposal、代码和有实质内容的报告/运行文档；说明中特别强调，不能根据文档运行的代码不会被评估。2010 的建议包括 OpenCV、ImageMagick、CUDA、FFTW、SQLite 和 libcurl，但这些只是时代样例。先按当前维护状态、平台和许可证重新选择；若不想承担 GPU 成本和驱动差异，选择 SQLite、libcurl 或另一个可在普通机器上复现的库更稳妥。

### 可运行项目包里应该有什么

项目在总成绩中占 50%，Lab 1 与 Lab 2 各占 15%，Homework 占 20%，课程没有考试。一个合格的站外项目包应包含固定版本或依赖范围、从干净环境构建的命令、最小演示输入、自动测试、预期输出、错误处理示例和内存检查结果。报告解释为何需要这个库、哪些资源由谁释放、性能或正确性如何测量；仅仅成功链接库不等于完成项目。

## 独立完成顺序：以可运行性推进

第一周完成 Lecture 1–5 与 Assignment 1–3，把编译、I/O、指针和结构体练到能解释每次转换。第二周完成 Lecture 6–10、Assignment 4–6b 与 Lab 1，集中处理动态内存、数据结构和库接口。第三周读 Lecture 11–14，完成 Assignment 7 与 Lab 2，再冻结 Final Project 的最小功能，先获得一次端到端运行，然后补测试、错误路径和文档。若三周过快，可以拉长日历，但不要改变依赖顺序。

最终目录最好能由一个脚本或简短命令重新构建和测试，却不要把测试框架包装成原课要求。保留原始题目编号、自己的提交版本、打开官方解答后的修改记录以及无法复现的 Athena/助教环节，读者才能分辨课程材料、个人实现和现代工具迁移。
