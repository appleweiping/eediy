## 第一关不是装环境，而是确认授权

课程题目涉及能真实影响设备与其他用户的数据通道。所有实验只允许在本人所有或得到明确书面授权、与生产环境隔离的设备和数据上进行；不得采集第三方浏览记录、恢复真实密钥、干扰共享服务器、绕过访问控制，也不得在生产机器上关闭缓解机制。Website fingerprinting 只用自建页面与本地受控标签页；Spectre、Rowhammer、ASLR 与 cache 实验没有合规实验环境时就停在模型和防御分析。一次“技术上可行”不是法律或机构规则上的授权。

这条边界也决定后面的学习分叉：能公开复现的工作进入代码与验证，依赖专用裸机或脆弱 DRAM 的工作停在 handout、trace 和防御模型。先写授权对象、设备所有者、隔离方式、允许的影响和停止条件，再决定是否启动实验；没有这些字段，环境搭得再完整也不应运行攻击负载。

## 再固定课程契约：Spring 2025

MIT 6.5950/6.5951 *Secure Hardware Design* 不是一门把密码学算法搬进 RTL 的课。它把微体系结构当作安全边界，讨论 cache side channel、transient execution、Rowhammer、hardware-software contract、fuzzing、formal verification 与 TEE，目标是同时回答“攻击为何成立”和“设计怎样消除那条信息流”。MIT OCW 课程主页把这一版标为 Spring 2025；适合已有 6.004 水平计算机体系结构和 C 调试能力的高年级本科生、MEng 与博士生，课内规格是 12 units、3-0-9。

版本必须写进学习记录。Spring 2025 没有 midterm 或 final，正式考核以 8 个实验为中心；研究生的实验占 85%、论文讨论占 12%、随机现场 checkoff 占 3%，本科生则是实验 97% 加 checkoff 3%。后续学期的累计考试不能倒填进这一版，也不能把 6.5950 与 6.5951 的身份差别误写成两套公开课程。本文是 R0 桌面研究，不声称完成过校内 checkoff、隐藏测试或专用机器实验。

## 公开材料能复原哪一条主线

[官方 calendar](https://shd.mit.edu/2025/calendar.html)给出的 14 讲从安全设计概览开始，依次进入 side channel、cache、transient execution、硬件—软件契约与缓解机制，再转向 physical attack、HSM、Rowhammer、软件安全的硬件支持、CPU fuzzing、formal verification 和 TEE。它不是“先学完攻击、最后一周再谈防守”的编排：合同、隔离、检测与验证应当紧跟相应攻击模型。自学笔记最好为每个主题保留 4 栏：资产、攻击者能力、泄漏或故障通道、可检验的防御性质。

## Lab 0–7 是 8 个实验，不是 6 个

[官方 labs 索引](https://shd.mit.edu/2025/labs.html)的说明文字仍写着 6 个 laboratory exercises，但同一页的表格实际列出 Lab 0 到 Lab 7，共 8 个；做计划应以逐项表格为准。Lab 0（5%）用 ASAN、UBSAN 或 Valgrind 调试 C 语言 note library；Lab 1（10%）在受控网页上收集 JavaScript trace 并做 website fingerprinting；Lab 2（20%）围绕 cache mapping、covert channel 与两类 cache attack；Lab 3（15%）研究 Spectre 的权限边界；Lab 4（15%）连接地址映射、真实 DRAM bit flip 与 Hamming(22,16) 缓解；Lab 5（10%）考察 ASLR bypass；Lab 6（15%）对修改过的 Pretty Secure Processor 做 RISC-V/RTL differential fuzzing；Lab 7（10%）用 Yosys 与 Rosette 检查同一处理器的算术错误和后门。

[官方 starter repository](https://github.com/CSAIL-Arch-Sec/SHD-StarterCode)公开了 Lab 0–7 的模板并采用 MIT License，但 solutions、gradebook 和 grading scripts 需要联系课程团队。Lab 2、Lab 3、Lab 5 依赖分配的 bare-metal arch-sec 机器，Lab 4 还依赖预先筛出的易受 Rowhammer 影响的 DRAM 与 HTCondor。虚拟机里跑通一个替代程序，不等于完成了原实验的物理假设和 checkoff。

Lab 6 还有一层独立的访问门槛。[官方 handout](https://shd.mit.edu/2025/labs/fuzz.html)和 starter code 可以公开审读，但原实验要求用课程分配的账号登录 `unicorn.csail.mit.edu`，并把程序送入课程提供的修改版 Pretty Secure Processor cycle-accurate RTL simulation。普通运行使用 `./run.sh partX`，不需要 debug port；只有选择 `./run.sh partX --debug` 调试路径时，才另外需要工作人员发放的 `SHD_DEBUG_PORT`。所以独立学习者能够审查 handout 与 starter code，却不能在缺少课程 Unicorn 和 PSP/RTL 基础设施时执行原 Lab 6；debug port 不是普遍前置。相比之下，[Lab 7 handout](https://shd.mit.edu/2025/labs/formal.html)明确把本地 Docker 列为 Unicorn 之外的运行方式。“仓库公开”只说明源码可见，不代表八个实验都能在本地运行。

### Lab 0 之前的 gate

1. 写一个跨 cache-line 访问的小型 C 程序，用 sanitizer 和 debugger 找出一处 undefined behavior，并解释错误为何不是“编译器随机坏掉”。
2. 给定虚拟地址、page size、cache set 数与 associativity，说明地址如何进入 page table、tag、index 和 offset；再区分 architectural state 与 speculation 留下的 microarchitectural state。
3. 读一段短 RISC-V 或 SystemVerilog 模块，为 reset 后的状态、合法 opcode 或加法结果写出一条 assertion 和一个反例测试。

若第 1 题不能稳定复现，先补 C 的内存模型、sanitizer 与 GDB；若第 2 题只能背术语，回到计算机组成、cache 和虚拟内存；若第 3 题读不出时序状态，先完成小型 RTL 仿真与 waveform 检查。这些是 EEDIY 前置诊断，不是官方实验。三题都通过后，再按 Lab 0 → Lecture 1–6 与 Lab 1 → 攻击/防御成对阅读 → Lab 6 handout/starter-code 审计 → Lab 7 本地可运行部分推进。没有隔离裸机时，Lab 2–5 只分析 handout、公开 trace 或自建模拟结果，不把这种降级路径写成原实验完成。

## 公开自学的完成声明应当分层

完成证据也要据实分层。公开条件下可以提交 Lab 0 与 Lab 7 本地 Docker 部分的代码、固定工具版本、测试和 waveform，以及 Lab 1 的合成或自有数据报告。Lab 6 只能形成有来源的 handout/starter-code 审计，除非学习者确实拥有课程发放的 Unicorn 凭证和课程 PSP/RTL 仿真基础设施；工作人员分配的 debug port 只在选择 `--debug` 时额外需要，不是普通运行或完成声明的必要条件。自行编写的本地 fuzzer 属于另一个 EEDIY 实验。对 Lab 2–5，只能提交威胁模型、handout 推导和模拟复核。不能获得的证据包括 Panopto 录像观看记录、Piazza 讨论、Gradescope 分数、工作人员隐藏测试、随机 checkoff、课程账户、专用服务器与官方 solutions。把这些缺口列在 README，远比用“全部完成”掩盖它们可靠。

## 如果目标是物理侧信道，改走 UNSW

[UNSW COMP6420 syllabus](https://cgi.cse.unsw.edu.au/~cs6420/syllabus/)走的是另一条硬件安全路线。[公开 Hackster 平台说明](https://cgi.cse.unsw.edu.au/~cs6420/hackster/)记录了一块定制板：iCE40 FPGA、运行 MicroPython 的 RP2040 应用微控制器、测量 FPGA 功耗的高速 ADC，以及作为 programmer 的第二颗 RP2040。这套平台支撑 scan chain、power analysis、fault injection、reverse engineering、logic locking 和 PUF；公开工具侧重 OSS-CAD/Yosys，并安排 5 个 labs 与 CTF。想研究 CPU cache、Spectre、Rowhammer、fuzzing 与形式化验证，优先 MIT；想研究密码实现与物理侧信道，且确有合规板卡和仪器条件，再选 UNSW。两者都不授权对第三方设备做测试。

## 结课件只比较两种防御验证

EEDIY 建议的结课项目是“自写小型 RISC-V/RTL 模块上的 fuzzing 与 formal verification 对照”，明确不是 MIT 官方 project。其中 fuzzer 是为无法公开执行的 Lab 6 路径自拟的 EEDIY 替代实验，不是 Lab 6 的移植或完成。只在仿真中植入一处有文档的算术或权限 bug：一侧写 differential fuzzer，另一侧写 formal assertion；保存触发输入、最小反例和 waveform，修复后让两套回归共同通过。交付包应含威胁模型、版本锁定、可重复命令、失败样例、修复 diff 和防御复盘；验收标准不是制造一个更隐蔽的漏洞，而是两条独立验证路径都能发现旧缺陷、拒绝错误修复，并在授权边界内解释残余风险。
