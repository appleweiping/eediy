### 课程重点

想学 hybrid model、temporal logic 与实现之间的关系，建议选 Berkeley EECS 149；想尽快写 POSIX real-time service，则改走 CU Boulder。EECS 149 的主教材是 Lee 与 Seshia 的 [Introduction to Embedded Systems](https://ptolemy.berkeley.edu/books/leeseshia/index.html)，当前页面提供 Second Edition version 2.3（2017）。全书从连续动力学、离散与 modal model 走到并发、调度、网络和安全，开发板只是实验载体。

这里借用的课程节奏来自 Fall 2015 archive：[logistics](https://ptolemy.berkeley.edu/projects/chess/eecs149/logistics.html) 记为 4 units，每周 3 小时 lecture 加 3 小时 lab，先修 EECS 16B 或 20、61C，以及 EECS 70 或 Math 55。公开录像只链接 Spring 2012/2011，不能当作 2015 同期内容。

### 教材、作业和旧 lab 要分层使用

[Lecture schedule](https://ptolemy.berkeley.edu/projects/chess/eecs149/lectures/index.html) 给出最可靠的阅读顺序，也能确认这些主题属于同一门课：continuous dynamics 与 sensing；discrete、modal、hybrid systems；automata、composition、temporal logic 与 reachability；最后进入 execution time、scheduling 和 concurrency。

[Homework index](https://ptolemy.berkeley.edu/projects/chess/eecs149/homework/index.html) 有 7 次题目但无答案。解答写明模型假设与推导，并用量纲、边界输入、仿真或 model checker 交叉核验。[Labs/project](https://ptolemy.berkeley.edu/projects/chess/eecs149/project.html) 则属于 2015 环境：WiiMote、NI myRIO、LabVIEW/MicroBlaze、CyberSim、Kobuki 和 Statecharts，Lab 1–7 后由 3–4 人做 final project。专有工具与 staff checkout 没有公开；下文只讨论怎样移植这些系统问题。

### 更换设备时必须保住 4 类证据

一阶 plant 从连续方程推导出离散更新式，controller 则写成 state machine；invariant、temporal
property 和 periodic-task schedulability analysis 约束这两个表示。仿真再注入 jitter、
missed deadline、sensor dropout 和 mode switch，用 event log 对照解析预期。

把同一模型写成四种可互查表示：连续方程、离散更新、automaton 与 executable simulation。
sample time 改变后重算近似误差，mode switch 前后写清 guard 与 reset；若故障注入打破 safety
invariant，沿 event log 找到最先失效的 assumption，而不是只看最终状态。

若希望接现代硬件，[Lingua Franca embedded labs](https://www.lf-lang.org/embedded-lab/) 用
RP2040 与 Pololu 3pi+ 2040 robot 训练反应式和实时控制。它是现代延伸，并非 Fall 2015
graded lab。无机器人时沿用相同 sensor/actuator 接口，同时在 deterministic simulation 旁
标出尚未测过的 latency、摩擦和电池行为。

### Berkeley 与 CU Boulder 各自解决什么

CU Boulder Coursera 是另一条以 Raspberry Pi、POSIX threads 和 Embedded Linux 为主的路线。要学 hybrid semantics、temporal logic、refinement 和 model checking，留在 Berkeley；要尽快实现 Linux real-time service，走 CU Boulder。

Berkeley 路线最合适的作品是一套“离散事件调度器 + 一阶 hybrid plant”：连续方程给出 plant，
automaton 负责 mode switch，调度器引入 deadline，再用固定 seed 重现一次 invariant failure。
真正值得比较的是同一次故障在方程、automaton 与 event log 中各出现在哪里；机器人是否会动反而
是次要问题。
