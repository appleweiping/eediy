# 可复现工程

“可复现”经常混在三个不同承诺里：同一源码能否产生逐字节相同的固件；同一数据能否算出容差内相同的指标；同一块硬件重测时能否落在预先规定的统计范围。三者需要的比较方法不同。把所有文件塞进容器，只会把没有定义的问题一起封装起来。

先拿一个包含输入数据、计算脚本和短报告的微项目练习。目标不是堆 CI 配置，而是让另一台机器从明确输入执行一个命令，得到指定输出，并在结果不同的时候知道该比较什么。

仓库中的 [RC 低通离线 starter](https://github.com/appleweiping/eediy/tree/main/examples/rc-lowpass)就是一个可直接重放的最小例子：在仓库根目录执行 `python examples/rc-lowpass/run.py`，即可在无网络、无第三方 Python 包的条件下生成解析数据、写入带校验和的来源记录、计算阶跃与 AC 指标，并按事先提交的容差验收。测试还要求两个空目录中的生成输入逐字节一致。

## 先说清楚要重现的是哪一种结果

对编译产物，可以采用严格定义：Reproducible Builds 项目的[定义](https://reproducible-builds.org/docs/definition/)要求在相同源码、构建环境和构建指令下，任何一方能重建逐字节一致的指定制品。只有在你列明“指定制品”与相关环境后，校验和相等才有意义；日志、签名或时间戳是否属于比较对象也要预先决定。

数值分析通常不应照搬逐字节比较。不同 BLAS、CPU 或并行归约顺序可能造成末位差异，此时应比较带单位的目标量、数组形状、守恒残差和有物理依据的容差。硬件更不可能复刻每个 ADC 样本，应固定板卡修订、固件、接线、校准与环境，并比较均值、离散度或频响边界。容差必须在看到第二次结果前写下，否则它只是为差异寻找借口。

为项目写三句话：

1. **输入是什么：**源码提交、原始数据校验和、参数文件和不可重建的外部模型；
2. **输出是什么：**固件、数值表、图和报告中真正支撑结论的部分；
3. **怎样比较：**逐字节、数值容差、结构性质或统计范围。

如果其中一句无法落地，先缩小主张，不要急着锁定更多依赖。

## 一次真正干净的重建会暴露隐式输入

给项目保留一个本地入口，例如 `make verify` 或等价任务，它从只读输入生成到新目录，并依次执行数据模式检查、计算、测试、作图和文档构建。然后在新克隆、空缓存和不同绝对路径下运行两次。过程中若偷偷读取用户目录配置、系统字体、网络上的“最新版”模型或上一次生成物，第二次运行就应该把它暴露出来。

Reproducible Builds 的[技术文档](https://reproducible-builds.org/docs/)列出时间戳、时区、区域设置、文件排序、随机性和构建路径等常见差异来源。不要一次性加一堆神秘环境变量；逐项改变日期、路径或 locale，观察哪一项进入输出，再在源头消除或明确记录它。固定随机种子只能重放同一随机序列，不能证明统计结论稳健；真正依赖 Monte Carlo 的结果还应在多个种子下检查分布。

依赖文件需要同时回答“想要哪个版本”和“实际取得了什么”。保存直接与传递依赖版本、下载来源和校验和；商业编译器、PDK、厂商模型或许可证服务器无法打包时，明确它们是外部前置条件，并提供合法的标准格式导出或可运行的缩小替代。容器可以描述用户空间，却不会自动记录 CPU 特性、仪器校准、USB 设备或远端服务状态。

## 来源记录要能解释一个产物，而不只是罗列文件

给每次重建生成一个小型 `run.json`：源码提交、入口命令、公开参数、已解析依赖、执行平台、开始时间、输入与输出校验和、工具版本，以及硬件运行 ID（若有）。SLSA 1.2 对[来源信息](https://slsa.dev/spec/v1.2/provenance)的定义强调可验证地追踪制品在哪里、何时以及怎样产生；小项目无需宣称满足某个 SLSA 等级，也可以借用“构建定义”和“本次执行信息分开”的思想。

许可证信息不要只写在 README 的一句“开源”。SPDX 3.0.1 的[范围说明](https://spdx.github.io/spdx-spec/v3.0.1/scope/)涵盖软件组成、构建信息、数据集、来源与完整性、许可证和版权。你未必需要完整 SPDX 文档，但至少要能回答每个外部库、模型和数据能否修改、重新分发、放进公开制品，以及版本变化后这些判断是否仍成立。

比较两次 `run.json` 时，把差异分成两类。时间、临时路径等不应影响指定输出的字段，应从输出中移除或归一化；编译器、输入校验和或硬件修订变化则必须保留，因为它们可能解释结果。有效的记录应让你从一个异常图追到本次输入与命令，也能从一次依赖变化找到所有应重新生成的产物。

## CI 是第二台机器，不是裁判

先让同一条本地命令可靠，再把它交给 CI。这样云端失败可以在本地缩小，而云服务停用也不会夺走项目的重建路径。CI 适合检查全新环境、多个平台和每次提交；它不适合自动给不可信贡献访问密钥、许可证服务器或连接实验硬件。

GitHub Actions 的[安全使用说明](https://docs.github.com/en/actions/reference/security/secure-use)要求谨慎处理不可信输入、给令牌最小权限，并指出把第三方 action 固定到完整提交 SHA 才能把引用当作不可变版本。对外部拉取请求，读取源码的任务与持有密钥或控制硬件的任务必须分开；日志也不能打印令牌、患者数据或厂商机密。自动硬件测试还需要独立限流、超时、急停和上电默认安全态，软件失败不能成为唯一保护。

最后做一次有意破坏：改变一份原始输入，确认依赖的图与报告会更新；删除一个外部工具，确认错误指出缺少什么；改变 locale 或工作路径，确认指定结果仍符合比较规则。另一台机器若能从空目录复现同类结论，并能把不可避免的差异解释到具体输入或平台，这套流程才真正有用。之后可把测量文件按[数据与实验记录](data-lab-notebooks.md)组织，或用[版本控制](version-control.md)保存这次可重建的里程碑。
