# C、CMake 与靠近硬件的程序

用一个环形采样缓冲区练 C 很合适：它在电脑上容易测试，接到 MCU 后又会立刻碰到中断、内存布局和吞吐量。典型故障是主机测试全部通过，上板后却丢样，甚至只在某个优化级别下出现。遇到这种情况，需要把算法、构建和硬件适配分开检查，而不是凭直觉责怪编译器。

| 练习边界 | 本页采用的对象 |
| --- | --- |
| 被测对象 | 固定容量的 `ring_buffer`，以及一层很薄的 ADC/DMA 适配器 |
| 可见症状 | 序号跳变、overflow 计数错误，或测试分支中的越界 |
| 对照环境 | 主机 debug/AddressSanitizer 构建与目标固件构建 |
| 核对结果 | 用固定输入重现故障，定位到接口、内存、构建或并发边界，并验证修复 |

环形缓冲区足够小，可以手工列出每个状态；同时又会暴露整数宽度、数组越界、回绕、错误返回和中断共享数据。故障调查从可在电脑上独立运行的核心模块开始，硬件只在后半程接回。

## 环形缓冲区先在电脑上通过边界测试

为采样数据写一个 `ring_buffer` 模块，只公开初始化、写入、读取和状态查询。容量、元素类型、满时覆盖还是拒绝、空读返回什么，都写进接口；不要让调用者通过阅读实现来猜。使用 `stdint.h` 的固定宽度类型可以表达存储意图，但它不会自动解决算术溢出、对齐或字节序，串行化格式仍要逐字节规定。

先在主机端测试空缓冲区、恰好装满、首尾回绕、连续溢出和非法参数。打开编译器警告时，不要照抄一串来源不明的 flags；从 GCC 的 [Warning Options](https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html) 查明每个选项检查什么，并记录实际编译命令。在 Clang 可用的平台，再按官方 [AddressSanitizer 文档](https://clang.llvm.org/docs/AddressSanitizer.html) 编译测试版本，让越界、use-after-free 等内存错误在主机上先失败。Sanitizer 是测试构建，不应直接成为目标固件的一部分。

把寄存器访问和计时器调用藏在很薄的平台接口之后。测试时由一个假接口产生样本；上板时才替换成真实 ADC 或 DMA 适配层。`volatile` 适合表达某些内存映射 I/O 访问，不能替代中断与主循环之间所需的原子性、临界区或内存顺序。若核心逻辑离开开发板就无法运行，通常说明算法和平台边界还没有切开。

仓库里的[固定容量 ring-buffer starter](https://github.com/appleweiping/eediy/tree/main/examples/ring-buffer)已经给出公开头文件、薄 ADC/DMA adapter、空/满/回绕/边界测试和独立故障目标。从 starter 目录运行 `cmake --workflow --preset host-sanitized`，会以 warning-as-error、ASan 和 UBSan 编译，再执行正常契约与负向测试。故障库故意在满时覆盖旧样本并返回成功；测试只有在探针真实退出 7 且打印观察到的契约破坏时才通过，因此文档里的预期日志不能代替执行。

## 看清 CMake 实际调用了什么

从空目录开始，只建立一个库目标和一个测试可执行文件。源目录保存 `CMakeLists.txt`，构建输出进入单独的 `build/`；删除这个目录后应能重新配置，而不需要手工复制头文件或调整 IDE 缓存。CMake 官方的 [逐步教程](https://cmake.org/cmake/help/latest/guide/tutorial/index.html) 从 executable、library 和 target linkage 开始，适合边做环形缓冲区边推进，不必先读完整本手册。

把 include 路径、编译定义和警告策略挂在需要它们的 target 上，避免全局 flags 让所有目标意外继承同一设置。测试也应成为构建图的一部分：配置、构建和运行测试分别有明确命令，测试失败要返回非零状态。查看 verbose build 输出，确认实际调用的是预期编译器；出现 undefined reference 时，先检查声明是否有对应定义、目标是否真的链接到库，以及静态库次序，而不是反复清缓存。

若几个人或 CI 需要共享同一套配置，可按官方 [CMake Presets](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html) 文档把项目级设置放进 `CMakePresets.json`，个人路径和本机选项留在不提交的 `CMakeUserPresets.json`。preset 解决的是“怎样重复同一次配置”，不会让不可移植的源代码变得可移植。

## 同一份核心源码保留主机和目标两种构建

主机测试通过后，再加入交叉编译器、toolchain file、链接脚本和启动代码。不要一开始就把它们揉成唯一构建。保留两个独立入口：

```text
host-debug  -> ring_buffer + tests + sanitizer
target      -> ring_buffer + hardware adapter + firmware image
```

两条路编译的是同一份核心实现，但回答不同问题。主机路适合大量边界测试和诊断；目标路检查 ABI、内存布局、启动过程、寄存器和实时约束。目标构建结束后阅读 map file 或 size summary，能指出代码、只读数据、已初始化数据、零初始化区和栈/堆预算大致落在哪里。映像“能够烧录”并不说明 RAM 没有越界，也不说明中断速率下不会丢数据。

上板前先用假中断连续产生样本，让消费端故意变慢，观察选择的 overflow policy 是否真的生效。上板后从保守时钟、限流供电和仍可恢复的调试接口开始；第一轮只比较已知输入下的序号、计数和错误码。若优化级别改变后才出错，优先怀疑未定义行为、未初始化数据和并发边界，而不是把优化关闭当作修复。

## 一次有用的调试记录应当留下什么

最后保留一条从新目录可执行的主机命令、一条目标构建命令和一次故意失败。故障可以是把容量改成边界值、让生产者快于消费者，或在测试分支中制造一次越界；测试应说明它为何失败。接口说明、测试日志、编译器版本、实际命令、映像尺寸和目标板/时钟信息足以让主机部分在没有开发板的环境中重跑。

原始症状、最小复现、根因、修复和回归测试应当能互相对应。[嵌入式工具链](embedded-toolchains.md)补充 ELF、烧录与启动链的调查方法；[版本控制](version-control.md)用于把算法、硬件适配和构建配置的变化拆成可追踪提交。涉及电机、加热、储能或射频发射时，软件测试永远不能替代硬件限位、超时、额定值检查和受监督设施。
