## First account for the speed of a three-week course

[MIT 6.087 Practical Programming in C, January IAP 2010](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/) is an intensive short course, not a first introduction to programming. Across three weeks it schedules 5 lectures of 1.5 hours and 1 laboratory of 3 hours each week. The stated preparation is basic programming experience from 6.00, 1.00, 6.01, or equivalent; prior C experience is neither expected nor desired. The course teaches C mechanisms, but it will not slowly introduce loops, functional decomposition, and debugging at the same time.

Use Assignment 1 from [Assignments](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/pages/assignments/) as a native readiness check. Complete syntax recall is unnecessary, but one should be able to compile a multi-function program at the command line, interpret a compiler line number, and narrow failure to input, control flow, or representation. If the edit–compile–run–inspect-exit-status loop cannot be completed independently, take an ordinary introductory programming course first rather than expecting three weeks to supply both algorithmic thinking and C’s memory model.

## How to read the fourteen lectures

[Lecture Notes](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/pages/lecture-notes/) publishes 14 slide sets and no lecture videos. The first part covers compiling and debugging, types, control flow and I/O, pointers, structures/unions/bit-fields, allocation, linked lists and trees, pointer-to-pointer use, arrays, stacks, and queues. The later part reaches function pointers, hash tables, libraries, B-trees, priority queues, the standard library, malloc internals and Valgrind, garbage collection, threads, sockets, asynchronous I/O, and Linux IPC. This breadth exceeds what can mature in three weeks; viewing Lecture 14 is not mastery of concurrency or networking.

Make every lecture leave at least one executable miniature whose lifetime, ownership, and failure paths can be explained. Draw addresses and targets for pointers, test both normal cleanup and error cleanup for allocation, and distinguish successful, partial, and failed operations for threads and sockets. The course used MIT’s Athena UNIX environment, which OCW does not provide. A present-day learner can use Linux, WSL, or a container with GCC/Clang, make, gdb/lldb, Valgrind, or supplemental AddressSanitizer/UndefinedBehaviorSanitizer checks. That is a modern migration, not the original 2010 MIT environment requirement.

## There are not eight assignments: 6a and 6b are two halves

The official description says the first two weeks contain 7 daily assignments, while the table has rows for Assignment 1, 2, 3, 4, 5, 6a, 6b, and 7—8 rows. Treat 6a and 6b as the two parts of Assignment 6 instead of rewriting the course as 8 assignments. Every group in the public table offers a solution or example for checking, with Assignment 7’s solution provided as a ZIP. Download only the prompt and required data first; open the official answer to compare interfaces, error handling, and data-structure choices only after local tests and a code review.

A current C-language mode, common warnings, and warnings-as-errors form a useful compile baseline, but should not be presented as an invented historical MIT command. For every assignment, run the applicable cases among ordinary input, empty or minimum-size input, boundary lengths, invalid input, and resource failure. Record not only stdout, but also exit status, stderr, leak/out-of-bounds reports, and which test actually exercised a branch.

## The two laboratories create one continuous testing story

### Lab 1: Game of Life has both public starter and solution

The [Labs](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/pages/labs/) page supplies both a starter ZIP and solution ZIP for Lab 1. The task reads a world and advances Conway’s Game of Life. The official check sets `NUM_GENERATIONS` to 50, runs `glider.txt` and `sship.txt`, inspects the resulting `world.txt`, and calls for a one-page report. Preserve the input files, build command, 50-generation output, and difference from the expected result. Passing these checks before viewing the solution is what makes the public answer useful for review.

This laboratory tests more than a two-dimensional array. Add boundary cells, an all-dead world, a stable form, and an oscillator; state the chosen boundary rule and run under a memory checker. If the starter interface or boundary semantics change, disclose that in the report. Otherwise, visually similar output cannot be compared directly with the official task.

### Lab 2: Huffman has no public solution

Lab 2 publishes a starter ZIP but no solution column. The in-lab decoder is expected to produce a `decoded.txt` containing `abbacafebad`; the subsequent project encoder must produce the specified codes and make the large decoded `decoded.txt` byte-identical to `book.txt`. Strong completion evidence is not a compression-ratio screenshot but a repeatable command sequence: encode, decode, compare with `cmp`, display exit status, and document behavior for an empty file, a one-symbol file, a file containing every byte value, and a truncated bitstream.

Preserve the absence of a Lab 2 answer. Round trips, independent miniature examples, prefix-property reasoning, and memory tools increase confidence, but a learner implementation is not the official reference implementation. The original laboratories involved pairs and staff signatures. The missing in-person questions, signatures, and paired debugging should not disappear behind a generic completion checkbox.

## The Final Project must run, not merely name a library

The [Final Project brief](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/9796fe2dda5404aa9d14a49081b842d8_MIT6_087IAP10_project.pdf) requires one or more open-source libraries, a one-page proposal, code, and a substantive report/run document. It specifically warns that code which cannot be run from its documentation will not be evaluated. The 2010 suggestions include OpenCV, ImageMagick, CUDA, FFTW, SQLite, and libcurl, but these are period examples. Reassess maintenance status, platform support, and license today. If GPU cost and driver variation are undesirable, SQLite, libcurl, or another ordinary-machine library is a more portable choice.

### What belongs in a runnable project package

The project counts for 50%, Lab 1 and Lab 2 for 15% each, and Homework for 20%; there is no exam. An outside project package should provide pinned versions or dependency ranges, a clean-environment build command, minimum demonstration input, automated tests, expected output, an error-path example, and memory-check results. The report should explain why the library is needed, who releases each resource, and how correctness or performance is measured. Successfully linking a library alone is not a project.

## Independent order: advance through runnable results

In week one, complete Lecture 1–5 and Assignment 1–3, practicing compilation, I/O, pointers, and structures until every conversion can be explained. In week two, complete Lecture 6–10, Assignment 4–6b, and Lab 1, concentrating on dynamic memory, data structures, and library interfaces. In week three, read Lecture 11–14, complete Assignment 7 and Lab 2, then freeze the Final Project’s minimum feature, obtain one end-to-end run, and add tests, error paths, and documentation. The calendar may be stretched, but the dependency order should remain.

The final directory should rebuild and test with one script or short command, without presenting that test harness as an original requirement. Retain official problem numbers, personal submission revisions, changes made after reading public solutions, and the unreproduced Athena/staff components. This makes course material, learner implementation, and modern tooling distinguishable.

## Cost, hardware, offline package, and licenses

The course itself requires no special hardware; an ordinary computer and a Unix-like environment suffice. A GPU or other device becomes a personal project cost only if the Final Project deliberately selects CUDA or a hardware-dependent library. [Download Course](https://ocw.mit.edu/courses/6-087-practical-programming-in-c-january-iap-2010/download/) preserves public notes, assignments, and laboratory attachments, but cannot restore Athena, classroom signatures, or staff support.

OCW files follow the license shown on the course site. Every open-source library used by the Final Project has separate license, NOTICE, linking, and redistribution conditions. Record dependency names, versions, and licenses in the README, and distribute only source and data for which permission exists. The course dates from January IAP 2010; system calls, compiler diagnostics, and library APIs may have changed. Document modernization patches separately instead of silently modifying an official starter and still calling it original.
