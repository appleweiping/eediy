### Course fit

Choose MIT [6.186 MASLab](https://ocw.mit.edu/courses/6-186-mobile-autonomous-systems-laboratory-january-iap-2005/) only for a short, intense robotics-systems sprint after Java/Linux, basic wiring, and state machines are usable. Beginners should first learn programming and embedded lab work. The archive documents January IAP 2005, when teams of 3–4 built an autonomous robot to find targets in an unfamiliar arena over 4 weeks. The [Syllabus](https://ocw.mit.edu/courses/6-186-mobile-autonomous-systems-laboratory-january-iap-2005/pages/syllabus/) schedules 15 sessions of 2 hours and explicitly says much work happens outside class.

### Checkpoints matter more than a contest video

The [Calendar](https://ocw.mit.edu/courses/6-186-mobile-autonomous-systems-laboratory-january-iap-2005/pages/calendar/) progresses through OrcPad hello world, edge/bump detection, feature detection, finding a red ball, a design checkpoint, scoring 1 point, 2 mock contests, and the final contest. At every stop, vary one condition and inspect raw telemetry before changing code. “Finds the red ball,” for example, needs distance, illumination, occlusion, and false-positive results—not only a successful clip.

[Assignments](https://ocw.mit.edu/courses/6-186-mobile-autonomous-systems-laboratory-january-iap-2005/pages/assignments/) also requires daily lab entries and a 5–10 page project report. Correlate hardware changes, software commits, parameters, and experimental results in one timeline so that an improvement can be attributed to algorithm, lighting, battery, or mechanics.

### Map every interface when replacing the old platform

The [kit contents](https://ocw.mit.edu/courses/6-186-mobile-autonomous-systems-laboratory-january-iap-2005/resources/kitcontents) and [lecture notes](https://ocw.mit.edu/courses/6-186-mobile-autonomous-systems-laboratory-january-iap-2005/pages/lecture-notes/) describe the 2005 OrcPad, old Java/CVS/Ant environment, camera, IR sensors, and motors. A current rebuild may use a differential-drive base or simulator, but must map each old sensor, actuator, and API and explain changes in latency, noise, and dynamics.

Proceed through sensor unit tests, actuator unit tests, odometry, offline vision, local behaviors, state machine, and whole-arena integration. Hold out a fixed frame corpus from vision tuning; test odometry on straight travel, in-place rotation, and a closed loop; save images, detections, pose, state, and motor commands together for every autonomous run.

### What the Two Mock Contests Reveal

Test motor direction with the chassis raised, cap PWM and current, and verify an emergency stop that survives a program crash. Without a suitable arena and supervision, complete the interfaces and mock contests in simulation and state that friction, lighting, and collisions remain unvalidated.

The platform mapping, BOM/wiring, calibration, checkpoints, daily log, telemetry from 2 mock contests, and final run should all describe the same robot. Official [Projects](https://ocw.mit.edu/courses/6-186-mobile-autonomous-systems-laboratory-january-iap-2005/pages/projects/) show how 2005 teams explained system tradeoffs. Today, the important question is how one recognition failure, one control oscillation, and one safety stop each changed the next run. The public archive does not include the old kit, arena, mentor feedback, or a runnable OrcPad environment; a modern build can inherit the checkpoint order, not the support conditions of 2005.
