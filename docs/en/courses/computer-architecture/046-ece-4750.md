## Preparation is more than “knows Verilog”

The Fall 2025 syllabus states three kinds of preparation: CS 1110 or equivalent programming; ECE 2300 or equivalent digital logic/computer organization; and ECE 3140 or equivalent systems programming. CS 3410 may substitute for part of the background, but the document notes that it lacks the same digital-logic depth and does not teach Verilog. Before beginning, one should be able to read and write combinational and sequential RTL, explain registers, memory, assembly, and basic pipelines, and use Python and version control from the command line.

The closest course-native check is the small Section 1 and Section 2 material in the public [2025F repository](https://github.com/cornell-ece4750/2025F). Read the Verilog/PyMTL3 multiplier interface, inspect one handshake trace with Verilator/GTKWave, run pytest, and add a boundary-input test. If `val/rdy` stalls cannot be explained, or only the final numeric value is readable while timing is opaque, review digital design and RTL verification. If the waveform is understandable but a Python test failure cannot be localized, review systematic debugging first. Public sections are warmups, not the complete starter for the 4 formal labs.

## Five theory parts should inform design decisions

The official syllabus organizes the theory into 5 parts: 6 lectures on processors, 5 on memories, 2 on system integration and networks, 12 on advanced processors, and 2 on advanced memories. The processor portion begins with ISA, datapath, control, and pipelining; memory moves into caches and main memory; integration places modules in communicating systems; the later parts address deeper parallel/out-of-order ideas, prediction, coherence, or more advanced memory hierarchies. Public pages expose T01–T11 lecture/problem handouts, but an outside learner should not infer that all classroom discussion, answers, and feedback are open.

For every subject, preserve one decision that could change an implementation. For pipelines, list detection conditions and treatments for each hazard. For caches, calculate tag/index/offset and predict hits. For multicore, state data partitioning and synchronization assumptions before running code. Otherwise 27 lectures become a vocabulary tour that cannot support cycle, CPI, or speedup explanations in the laboratories.

### Lab 1 and Lab 2: make interfaces and pipeline behavior visible

The [Lab 1 iterative multiplier](https://www.csl.cornell.edu/courses/ece4750/handouts/ece4750-lab1-imul.pdf) asks for fixed- and variable-latency designs with 32-bit operands/results and a `val/rdy` interface. The baseline FSM shown in the brief takes a fixed 35 cycles per operation. Tests should check not only multiplication values but the cycle in which a request is consumed, response stability under backpressure, spurious data after reset, and whether the variable-latency optimization actually reduces cycles for chosen inputs. A report needs a functional test table, representative traces, and cycle comparison; one random test is not protocol verification.

Lab 2 builds two 5-stage TinyRV2 processors: one stalls for dependencies, while the other adds bypassing, and both implement 27 of 34 TinyRV2 instructions. Beyond correctness, divide data/control hazard tests into categories and compare cycles and CPI with identical programs. Without the Cornell starter, an independent implementation must recreate interfaces, memory model, and test programs. It can be labeled a personal implementation based on the brief, but not “passed Cornell hidden tests.”

### Lab 3 and Lab 4: cache behavior becomes a multicore experiment matrix

Lab 3 compares a direct-mapped write-back/write-allocate cache with a 2-way set-associative cache. Directed address sequences should separately create compulsory, conflict, and capacity behavior and test dirty eviction, refill, and blocked responses. Random reads and writes alone can hide controller errors. Performance discussion should connect hit rate, miss penalty, and total cycles for named workloads instead of merely declaring that “2-way is faster.”

The [Lab 4 multicore system](https://www.csl.cornell.edu/courses/ece4750/handouts/ece4750-lab4-sys.pdf) composes processors, caches, and a ring network into single-core and 4-core systems and runs single- and multithreaded sorting. Its analysis specifies 5 configurations/experiments across 5 microbenchmarks: 25 runs producing 2 bar plots, speedup and CPI. Every bar should trace back to a raw log, configuration, commit, and random seed. If the full scaffold is unavailable, an independent project may narrow scope, but must not silently call the smaller experiment completed Lab 4.

## Begin outside Cornell with Section code, not a fictional Cornell environment

First run 2025F Section 1/2 from the official repository, recording tool versions, build commands, pytest output, and one annotated `val/rdy` trace. Then use the official Lab 1 brief to begin a multiplier in a personal repository with the interface and test plan. Cover at least 0, 1, maximum unsigned values, sign-bit patterns, consecutive requests, response backpressure, and reset boundaries. Read the Lab 2, 3, and 4 briefs next, choose either “recreate tests and microarchitecture models only” or “gradually recreate scaffolding,” and state omissions in the README.

Proceed through Lab 1 multiplier, Lab 2 pipeline, Lab 3 cache, and Lab 4 integration while interleaving the relevant theory. Preserve at every stage a requirement-to-test mapping, minimized failing tests, traces or event logs, correctness results, cycle/CPI data, and design tradeoffs. Lab 4’s 25 runs and 2 plots are course-specific performance evidence. If the machine, cross compiler, or full system is absent, stop honestly at an earlier layer rather than generating fictional performance numbers.
