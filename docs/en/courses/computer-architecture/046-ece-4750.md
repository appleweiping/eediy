[syllabus](https://www.csl.cornell.edu/courses/ece4750/handouts/ece4750-syllabus.pdf),
4 lab briefs, and public 2025F code. It is a main course in connecting
microarchitecture through Python/PyMTL3, Verilog, pytest, waveforms, and
performance experiments. It assumes programming, digital logic and
organization, and systems-programming foundations.

Use Sections 1 and 2 in the official
[2025F repository](https://github.com/cornell-ece4750/2025F): read the
multiplier's `val/rdy` interface, inspect a handshake with
Verilator/GTKWave, and add one boundary case to pytest. These tasks expose the
assumed foundation directly; review RTL and verification if backpressure or
the first failing cycle cannot be explained. Public sections are warmups, not the complete starter for the 4
formal labs.

### Labs and projects

The [lab logistics](https://www.csl.cornell.edu/courses/ece4750/handouts/ece4750-lab-logistics.pdf)
describe teams of 2, private GitHub repositories, milestones, checkoffs, and
staff feedback. An outsider can read briefs but not recover the complete
starter, `ecelinux`, Canvas, private CI, or instructor tests.

[Lab 1](https://www.csl.cornell.edu/courses/ece4750/handouts/ece4750-lab1-imul.pdf)
builds a 32-bit fixed- and variable-latency iterative multiplier; the baseline
FSM takes 35 cycles. Test request acceptance, response backpressure, reset,
and cycle reduction as well as products. Lab 2 builds stall and bypass
versions of a 5-stage TinyRV2 processor and compares hazards, cycles, and CPI
on identical programs. Lab 3 compares direct-mapped and 2-way
write-back/write-allocate caches with directed compulsory, conflict, capacity,
and dirty-eviction traces.

[Lab 4](https://www.csl.cornell.edu/courses/ece4750/handouts/ece4750-lab4-sys.pdf)
combines processors, caches, and a ring network into single-core and 4-core
systems. Its analysis uses 5 configurations across 5 microbenchmarks: 25 runs
and 2 speedup/CPI plots. Every bar should trace to a raw log, configuration,
commit, and seed. If the full scaffold is absent, narrow the implementation
and state omissions instead of inventing 25 results.

### Rebuild Tests First, Then Choose How Much Hardware to Recreate

Record the Section environment, commands, pytest output, and one annotated
handshake trace. Then implement Lab 1 independently from the public
interface and a requirement-to-test map. For Labs 2–4, choose explicitly
between recreating tests and microarchitecture models only or rebuilding the
scaffold layer by layer. Preserve minimized failures, waveform or event logs,
correctness regressions, cycle/CPI data, and design decisions.

Theory must drive those decisions: state pipeline hazard conditions and
treatments, split cache tag/index/offset, and define multicore partitioning
and synchronization. Watching 27 lectures without traces and measurements
cannot explain the labs.

### Every Performance Claim Must Reach Raw Evidence

The labs are simulation-centered; do not invent an FPGA purchase. Record tool
and cross-compiler versions. Because the public repository root declares no
license, link to it rather than mirroring teaching code. A genuinely
independent implementation can be licensed separately while excluding Cornell
materials.

At minimum, finish multiplier protocol tests, a pipeline hazard matrix, one
directed cache trace, and an integration experiment at the available scope.
Report correctness, cycles, CPI, and clock and memory assumptions together,
and link one failed waveform directly to the corresponding design decision.
Explaining why an optimization helps only particular inputs is a better result
than claiming to have passed unavailable Cornell hidden tests.

The baseline and optimization must share one commit lineage, workload, and
timing boundary, with raw logs attached. Rebuild the baseline whenever tool
options, the memory model, or the input distribution changes; otherwise a
cycle or CPI difference cannot be attributed to the design.

Compare functional tests, cycle traces, the synthesized clock constraint, and
end-to-end runtime under the same workload. Without all four, a bottleneck
cannot be assigned to the microarchitecture, tool constraints, or measurement
window.
