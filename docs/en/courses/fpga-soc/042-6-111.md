## Start with the Four Labs, Not the Verilog Topic List

MIT 6.111 is a digital-systems laboratory and project course. The first part of
the Spring 2006 version covers combinational logic, Verilog, sequential
modules, FSMs and synchronization, memory and timing, arithmetic structures,
analog building blocks, integration, reconfigurable logic, video,
performance transformations, and digital-system power. During the final 5
weeks, normal lecture and recitation stop and the schedule is devoted to the
final project. The official
[calendar](https://ocw.mit.edu/courses/6-111-introductory-digital-systems-laboratory-spring-2006/pages/calendar/)
shows the balance better than the lecture titles do: Verilog is only the
opening tool. Interfaces, clocks, synchronization, verification,
decomposition, and debugging consume the semester.

The [syllabus](https://ocw.mit.edu/courses/6-111-introductory-digital-systems-laboratory-spring-2006/pages/syllabus/)
says that prior digital-design experience and 6.004 are not required, although
basic circuit theory is. “No prior experience” should not be read as “learn
logic gates and programming from zero during Lab 1.” A learner should already
be able to read a combinational truth table, explain edge-triggered register
updates, express state and data flow in a programming language, and read a
basic oscilloscope trace.

If I had to choose between neighboring courses, I would use
[MIT 6.004](../digital-logic/037-6-004.md) or DDCA to fill gaps in HDL and
computation structures. I would choose 6.111 for a learner who can already read
basic timing diagrams and wants to carry an FPGA design through demonstration
and technical reporting.

## What Labs 1–4 Actually Build

The [labs](https://ocw.mit.edu/courses/6-111-introductory-digital-systems-laboratory-spring-2006/pages/labs/)
include PDFs, Verilog templates, `.ucf` pin constraints, and support modules.
Each lab adds a concrete piece of the later project work:

1. **Lab 1: basic digital design** establishes synthesis, download, board I/O,
   and checkoff, confirming that the toolchain, constraints, and board wiring
   work together.
2. **Lab 2: traffic-light controller** makes states, inputs, and timing
   observable through an FSM.
3. **Lab 3: memory tester** introduces protocol, address and data paths, active
   read/write control, and error reporting.
4. **Lab 4: Pong video game** combines a complex FSM, video timing, input, and
   display in the first substantial integration exercise.

The three problem sets mainly prepare those labs, and
[Assignments](https://ocw.mit.edu/courses/6-111-introductory-digital-systems-laboratory-spring-2006/pages/assignments/)
provides solutions; the course also has one formal quiz. Work the matching
problems before opening a lab template. Otherwise a blank display can leave
timing concepts, constraints, and wiring faults tangled together.

## The Checkpoints Before the Final Demo

The syllabus calls these figures an **approximate breakdown**: the final
project contributes about 37%, and the four labs together contribute about
37%. A team of 1–3 moves through team formation, abstract, proposal
conference, block-diagram conference, design presentation, custom checklist,
implementation and debugging, final demo or video, and report. Even an
incomplete project must be demonstrated and documented to pass. Explaining
what failed, where it failed, and what remains is part of the submission.

The official
[Projects](https://ocw.mit.edu/courses/6-111-introductory-digital-systems-laboratory-spring-2006/pages/projects/)
page presents fifteen Spring 2006 examples, including a boxing game, drum
machine, fingerprint verification, 3-D Pong, active sonar, karaoke, video
surveillance, and CDMA decoding. Use them to study the relationship among
block diagrams, presentations, final reports, and demonstrations. They are not
fifteen modern one-command reproductions.

Independent study cannot reproduce the TA conferences, but it can keep 3
written checkpoints: freeze requirements, interfaces, and clock domains; show
a minimum demonstrable slice while reviewing the verification plan and
resource budget; then run the custom final checklist. These are not MIT course
activities, but they preserve more of the project cadence than waiting until
the last week for the first board test.

## Porting the 2006 Labkit to Current Hardware

The original labkit used a Xilinx Virtex-II and ISE Foundation. The official
phrases “6 million gates” and “state-of-the-art” belong to 2006; `.ucf`
constraints, video,
memory, and support modules are also board-specific. The old labkit
documentation deep link now redirects to the MIT MTL home, and copyrighted
device data sheets were not bundled. Claiming that the labs run unchanged on a
modern board would hide the most important work.

Start with a migration matrix that maps the original device, interfaces,
clocks, memory, and constraint format to the new platform. Verify clock, reset,
one I/O, video timing, and memory separately before moving application logic.
A clean synthesis only says that the synthesizer accepted the design; keep the
timing reports, CDC assumptions, resource use, simulation tests, and board
checkoffs as well. Keep board work low-voltage, power down before rewiring, and
exclude unknown PMOD modules, power rails, lasers, and high-power peripherals.

### A Project Record Someone Else Can Check

Using a video or communications system from the 2006 project page as the
reference, keep a block diagram with module ownership and clock domains,
interface and timing agreements, automated testbenches, synthesis and timing
reports, staged checkoffs, a fault log, final demo, and technical report. A
directory of Verilog files alone does not show whether the design ever ran on
the board or which interface failed.

[Exams](https://ocw.mit.edu/courses/6-111-introductory-digital-systems-laboratory-spring-2006/pages/exams/)
provides the course quiz and 2003/2004 practice exams for checking timing,
FSM, memory, and system concepts. The
[course home](https://ocw.mit.edu/courses/6-111-introductory-digital-systems-laboratory-spring-2006/)
ties the syllabus, calendar, and project material together. Before starting,
pick an FPGA that is actually obtainable and well documented, then decide
whether rewriting constraints and board interfaces is part of the project you
want. If the goal is to follow the old PDFs unchanged, this 2006 course is not
the easy option.
