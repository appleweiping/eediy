## Separate RP2350, RP2040, and PIC32 Before Starting

Cornell ECE 4760/5730 is not a course that can be completed by watching
embedded-systems videos. The [current course home](https://ece4760.github.io/)
calls it a Cumulative Design Experience: teams of 2–3 put
differential equations, DSP, analog circuits, control, graphics, and
mechatronics into physical systems. On the review date, it names the RP2350 on
the Raspberry Pi Pico 2 as the current MCU. The same page, however, publishes
2025 and 2022 recordings labeled RP2040 and retains a 2021 PIC32 site. Some
installation notes and the BOM also still say Pico or RP2040. Peripheral
continuity does not make registers, pins, SDK targets, and board wiring
interchangeable. Record the chosen version in the repository README, CMake
target, board photograph, and datasheet before writing application code.

The three laboratory pages do not carry identical version labels. Birdsong
explicitly links a Fall 2025 RP2350 version; this guide treats the Galton
Board and Helicopter pages as the current RP2350 writeups visible at review
time without assigning them a semester. The 2025 RP2040 recordings are
conceptual supplements. If an example only builds for RP2040, isolate it on a
separate branch and document the difference instead of silently changing it
and claiming a current-lab reproduction. The PIC32 archive is useful for
ideas, not current starter code.

## The Three Labs Are Not Peripheral Demos

The course is not a collection of unrelated peripheral demonstrations. Each
of its 3 laboratories occupies about 3 weeks with cumulative checkpoints,
followed by a 4–5-week final project.

The first is [Birdsong](https://vanhunteradams.com/Pico/Birds/Birdsong.html):
use DDS, fixed-point arithmetic, an SPI DAC, a keypad, and a debounce state
machine to synthesize a cardinal song whose dominant frequencies sweep
roughly 2–7 kHz. “The speaker makes sound” is not sufficient; spectrum, sweep
timing, and interaction need defensible specifications. The
[Digital Galton Board](https://vanhunteradams.com/Pico/Galton/Galton.html)
then simulates collision physics and a binomial distribution on a 60 fps VGA
display while DMA plays a sound for every impact. Moving-ball count, frame
rate, and distribution error make performance visible. Finally, the
[1D Helicopter](https://vanhunteradams.com/Pico/Helicopter/Helicopter.html)
combines an I2C IMU, complementary filtering, PWM, optical isolation,
serial/VGA output, and PID control. Its first checkpoint already requires the
mechanical assembly, open-loop motor control, and a dedicated motor PCB.

That order deliberately moves from deterministic waveforms to concurrent
simulation and then to a physical controller that can oscillate or injure.
An independent learner should not select only the photogenic helicopter.
Otherwise DMA, fixed point, display timing, and disciplined debugging first
appear on the highest-risk apparatus.

## Compile a Demo and Measure Its Waveform First

The [policy](https://vanhunteradams.com/Pico/CourseMaterials/Policy.html)
requires ECE 3140 or instructor permission and explicitly expects C,
electronic construction, and substantial mathematics. Instead of inventing a
generic entrance test, build one current RP2350 course demo, make the Pico 2
produce a periodic GPIO or PWM signal, and save an oscilloscope trace with
time scale, voltage scale, and probe location. A successful compile with no
pin waveform points toward the board target, pin map, or power. A waveform at
the wrong frequency points toward the clock, timer, or integer calculation.
This short loop exercises C/CMake, datasheet use, board wiring, and
measurement in the same way the labs do.

If compilation is the block, review pointers, headers, CMake, and debugger
use. If GPIO is correct but the SPI DAC is silent, measure SCK, MOSI, CS, and
the DAC output separately before changing synthesis code. If range,
logic-level, and timing tables are unreadable, practice with datasheets
first. Policy expects each team member to understand every system part; an
individual repository should likewise keep the hardware version, controller
parameters, and report tied to the same configuration.

## Reconstruct It in Hardware-Risk Order, Not Calendar Order

First lock the SDK and board target and compile a course demo. A rebuild
record should name the SDK commit, compiler/toolchain version, selected board
or CMake preset, and the exact configure and build commands. `CMakeCache.txt`
contains local paths and probe results and is not a portable project input.
For Birdsong, generate a reference spectrum in a host script before attaching
the DAC, keypad, and speaker.

For the Galton Board, use a fixed random seed only as a regression: an
unchanged build should reproduce the same trajectories while timing and
collision code are compared. It does not validate randomness. Repeat the run
with many independent seeds and compare empirical mean, variance, and the
landing histogram with the expected binomial distribution. Then add VGA,
DMA, and sound and use timestamps or logic-analyzer traces to show that the
60 fps loop does not block. Keep the course's own rhythm of pre-reading,
weekly progress, final demo, and report rather than imposing a generic
workflow.

The helicopter should not be the default physical assignment for an
unsupervised learner. Test PID first with a software plant, recorded IMU data,
or a low-power fixture with limited travel. Before a physical build, read the
[Motor Circuit](https://vanhunteradams.com/Pico/Helicopter/MotorCircuit.html)
line by line: the MOSFET gate is driven from 12 V on the isolated side, while
the motor uses 5–6 V; processor and motor sides use separate supplies and
separate grounds. Never put the motor-current path on a solderless
breadboard—populate the course PCB and verify 4N35, MOSFET, and flyback-diode
orientation. Wear safety glasses and use fume extraction while soldering.
The fixture also needs travel limits or a guard, current limiting, and an
emergency stop. Before powering the ducted fan, verify open-loop direction,
the PWM-off state, and IMU sign. The dedicated PCB, teaching fixture, and
in-person TA are conditions that a public webpage does not supply.

## Follow the Proposal, Weekly Reports, Demo, and Final Webpage

The [Final Project page](https://vanhunteradams.com/Pico/CourseMaterials/Final_Project.html)
requires a 2–5-page proposal with tentative cost, block diagram or
schematic, societal impact, standards, safety, IP, and radio-compliance
considerations. Weekly reports state accomplishments, next objectives, and
hours. The official guidance estimates 16–20 hours per week for the last
4–5 weeks—a 4-credit team-course workload, not a weekend build. The
final webpage is supposed to let a technical reader reconstruct the system
and include test data, scope traces, speed and accuracy, failed attempts, AI
use, code attribution, and division of labor.

The course grade is 50% labs and 50% final project. Within each lab, the
debugging quiz is 10%, weekly progress 20%, final demo 30%, and report 40%;
working code alone therefore completes only part of a lab. The project page
contains a separate contradiction: its top navigation says progress 20%,
demo 30%, and report 50%, while the body and current policy both say
preparedness 10%, progress 20%, demo 30%, and report 40%. The body and policy
agree, so this guide uses 10/20/30/40 and records the stale navigation.

An independent learner need not invent Cornell grades. Follow those native
items directly: the proposal should establish parts and risk preparation;
weekly entries should show actual progress; the demo should repeat from power
off; and the HTML report should include scope traces, speed or accuracy data,
failed attempts, and a hardware/software tradeoff. This preserves the
course's design rhythm without applying one checklist to every project.

The project webpages span 1999–2025. The 2025 list alone includes audio
localization, BLDC control, oscilloscopes, robots, vision, and networked
devices. Use them to calibrate scope and report structure, not as
unacknowledged source code. Current policy also forbids sharing unprotected
lab code between groups; reused public final-project code still requires
detailed attribution.

## Budget, Safety, and Gaps in the Public Release

The official course material implies that a minimum kit is more than a Pico 2.
Depending on the lab it includes a
breadboard or protoboard, wiring, USB-UART or debugger, VGA display, DAC,
keypad or encoder, IMU, motor drive, mechanical hardware, power supplies, and
measurement tools. The linked legacy BOM still lists the original Pico,
micro-USB, and shared displays; it is not a current personal RP2350 shopping
list. Make a separate BOM for each lab, verify logic levels and availability,
then obtain prices. The final project also needs a spending ceiling and
substitute parts. Without an oscilloscope, current-limited bench supply, and
safe fixture, complete the software and low-voltage portions of the first 2
labs and submit a simulated helicopter instead of improvising a hazardous
mechanism.

The official public course site gives learners lab writeups, demo code,
datasheets, lecture links, and many student reports, but not Canvas
submissions, lab equipment, TA checkoffs, or Cornell-supplied material. A
finished run should show version locks, source, schematics, raw measurements,
checkpoint records, and reports for all 3 labs, plus the final-project
proposal, BOM, risk table, weekly status, demonstration video, and HTML
report. Compiling a few peripheral demos remains preparation, not the
course's cumulative design experience.
