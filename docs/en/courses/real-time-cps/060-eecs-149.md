### Course focus

Choose Berkeley EECS 149 for hybrid models, temporal logic, and their relation to implementation; choose CU Boulder for a quicker route to POSIX real-time services. EECS 149 centers on Lee and Seshia’s [Introduction to Embedded Systems](https://ptolemy.berkeley.edu/books/leeseshia/index.html), whose page offers Second Edition version 2.3 (2017). It moves from continuous dynamics and discrete or modal models to concurrency, scheduling, networks, and security. The board is only an experimental carrier.

The course rhythm here comes from the Fall 2015 archive. [Logistics](https://ptolemy.berkeley.edu/projects/chess/eecs149/logistics.html) records 4 units, with 3 lecture hours and 3 lab hours each week, and prerequisites of EECS 16B or 20, 61C, plus EECS 70 or Math 55. Public recordings link only Spring 2012/2011 and are not contemporaneous 2015 lectures.

### Use the textbook, homework, and old labs at different layers

The [lecture schedule](https://ptolemy.berkeley.edu/projects/chess/eecs149/lectures/index.html) gives the most reliable reading order: continuous dynamics and sensing; discrete, modal, and hybrid systems; automata, composition, temporal logic, and reachability; then execution time, scheduling, and concurrency.

The [homework index](https://ptolemy.berkeley.edu/projects/chess/eecs149/homework/index.html) has 7 sets without answers. State model assumptions and derive each result before checking with dimensions, boundary inputs, simulation, or a model checker. The [labs/project](https://ptolemy.berkeley.edu/projects/chess/eecs149/project.html) belong to the 2015 environment: WiiMote, NI myRIO, LabVIEW/MicroBlaze, CyberSim, Kobuki, and Statecharts, followed after Lab 1–7 by a 3–4 person final project. The proprietary tools and staff checkout are not public, so the discussion below focuses on porting the underlying system questions.

The course Resources page directly recommends Antonio Iannopollo's
[eecs149_spin](https://github.com/ianno/eecs149_spin). This BSD-3-Clause
repository contains a Fall 2014 cruise-control state machine, a
nondeterministic environment, and 4 LTL properties; it is not a source of
2015 homework answers. Before changing a threshold or transition, predict
which property will break; then inspect SPIN's counterexample trace and map it
back to the invariant and environment assumption.

### Preserve Four Kinds of Evidence When Equipment Changes

Derive a discrete update from a first-order continuous plant, then express its controller as a state machine. Give it an invariant and a temporal property, and perform schedulability analysis for periodic tasks. Finally inject jitter, missed deadlines, sensor dropout, and mode switches in simulation, comparing analytic expectations with an event log.

Write the same model in four cross-checkable forms: continuous equations,
discrete update, automaton, and executable simulation. Recalculate
approximation error after changing sample time, and spell out guards and resets
around every mode switch. If fault injection breaks a safety invariant, follow
the event log to the first failed assumption instead of reading only the final
state.

For current hardware, the [Lingua Franca embedded labs](https://www.lf-lang.org/embedded-lab/)
use RP2040 and the Pololu 3pi+ 2040 robot for reactive and real-time control;
they are a modern extension, not Fall 2015 graded labs. Without a robot, keep
the same sensor/actuator interfaces and mark the unmeasured latency, friction,
and battery behavior beside the deterministic simulation.

### What Berkeley and CU Boulder Each Emphasize

The CU Boulder Coursera course is an alternative centered on Raspberry Pi,
POSIX threads, and Embedded Linux. Stay with Berkeley for hybrid semantics,
temporal logic, refinement, and model checking; use CU Boulder to implement
Linux real-time services sooner.

A fitting Berkeley project is a discrete-event scheduler plus a first-order
hybrid plant: continuous equations define the plant, an automaton handles mode
switches, the scheduler introduces deadlines, and a fixed seed repeats one
invariant failure. The useful comparison is where that same fault first appears
in the equations, automaton, and event log; whether the robot moves is secondary.
