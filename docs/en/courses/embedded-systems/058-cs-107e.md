## From Machine Code to an Interactive Bare-Metal System

Stanford CS107E is the hardware and embedded variant of CS107. It starts with
RISC-V instructions and machine code, then builds a C environment,
compile/link/load path, memory management, and bare-metal peripherals until a
board with no operating system becomes an interactive personal system. The
current public site is Spring 2026. In 2024, the course moved from Raspberry
Pi/ARM to the AllWinner D1 RISC-V SoC on a Mango Pi MQ-Pro. It is neither an
introductory C course nor a collection of unrelated Raspberry Pi projects.

The official [About](https://cs107e.github.io/about/) page names information
representation, program execution, peripheral control, command-line tools, and
C as outcomes. The prerequisite is CS106B or equivalent: recursion, pointers,
linked lists and trees, abstract data types, stacks, queues, sets, maps,
searching, sorting, and hashing. A practical check is whether a learner can
read pointer-heavy C/C++ without an IDE, recover a mistaken Git change, and
explain stack versus heap on paper. If all three are weak, hardware, C, and
toolchain failures become inseparable.

## Seven Assignments Grow One System

[Assignments](https://cs107e.github.io/assignments/) begins with Assignment 0
for Git and environment setup. The next seven assignments evolve the same
bare-metal library:

1. **Larson Scanner** introduces GPIO/MMIO and RISC-V machine control.
2. **Clock** establishes timing, display, and module boundaries.
3. **String Formatting** builds UART and string infrastructure so the system
   can report its own state.
4. **Stack and Heap** enters calling convention, memory layout, and allocation.
5. **Keyboard and Simple Shell** adds a PS/2 keyboard and command interaction.
6. **Graphics Library and Console** operates the framebuffer and turns text and
   graphics into a reusable layer.
7. **System Monitor with Interrupts** combines GPIO interrupts, the keyboard
   driver, and interrupt-safe structures into an interactive console.

A2–A7 continuously extend `libmymango`; later work depends on earlier
interfaces and implementation. Skipping one removes infrastructure rather than
one independent exercise. The official historical estimate is 10–20 hours per
weekly assignment, a strong warning against pairing the course with several
other project-heavy courses.

## Labs Put the Hard-to-Debug Parts on the Bench

[Labs](https://cs107e.github.io/labs/) lists Lab 0–9: Orientation, meeting the
Mango Pi, Below C Level, Debugging and Testing, Linked and Loaded, Keyboard
Surfin’, Drawing into the Framebuffer, Mango Pi Interrupted, and two project
meetings. In the enrolled course, labs are two-hour paired sessions graded for
participation and prepare that week’s assignment.

At home, the “prelab → guided exercise → check-in” pattern is still useful.
Predict registers and observations, run the exercise, then explain what failed
and what changed. Without staff reference implementations or a lab partner,
each driver needs its own observation point: UART logs, GPIO logic capture, minimal test
programs, and a fault tree. A blank display alone cannot distinguish a linker,
clock, pin, protocol, or memory-corruption failure.

## The Final Project Continues the First Seven Weeks

The final project is normally a two-person, two-to-three-week hardware/software
system built on the library from the first seven weeks. The
[Project](https://cs107e.github.io/project/) proposal requires core, stretch,
and fallback goals, a material budget, ownership, risk-ordered schedule, and a
midpoint milestone. Final delivery is a live demo, code, and README. The rubric
assesses Challenge/Technical Achievement, Execution, and
Originality/Artistry. There is no exam; integration is the assessment.

When showing the project to someone else, bring a BOM and interface diagram,
the three scope levels, a minimum prototype for the hardest part, milestone
notes, repeatable build instructions, a fault log, demo, and README. External or
AI-assisted final-project code must identify source and personal contribution.
Course policy permits AI for background explanations with citation for
assignment-specific help, but prohibits sending assignment code to AI or
submitting generated assignment code.

## Check What You Can Actually Access

Spring 2026 has two 90-minute lectures and one two-hour lab each week. Lectures
are not recorded, no remote/SCPD version exists, and enrollment is capped at 40
with a questionnaire and instructor consent. The official
[Stanford FAQ](https://web.stanford.edu/class/cs107e/) describes a kit
containing the SBC, breadboard, jumpers, LEDs, and transistors; the 2025–26
price is $75 and the SBC is returned. Public visitors can read writeups,
[Schedule](https://cs107e.github.io/schedule/), and guides, but they cannot
access the enrolled-course repository or receive staff implementations, formal
QA, Ed support, in-person lab, or the full kit.

## Check the Toolchain Before Buying a Board

The Assignments FAQ still contains “cross-development tools for arm
processors,” while the 2026 home, schedule, slides, and About page all specify
RISC-V. Treat that as stale migration text, not evidence that the current
course is ARM. Hardware, fee, and return policy are also term-specific.

I recommend checking that the public toolchain runs on your system and that the
missing starter and reference code is acceptable before buying a Mango Pi. The public
writeups are enough to understand how the course grows, but without the course
repository, QA, and lab kit, this remains a careful public reconstruction—not
the enrolled Stanford experience.
