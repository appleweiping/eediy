### From Machine Code to an Interactive Bare-Metal System

Choose Stanford [CS107E](https://cs107e.github.io/about/) if C is already comfortable and you want to build a runtime, allocator, and interrupt library yourself; learn pointers in a conventional systems course first otherwise. CS107E moves from RISC-V instructions, the C runtime, linking, and loading through memory, peripherals, interrupts, and a personal system. Spring 2026 uses the AllWinner D1 Mango Pi MQ-Pro; the course migrated from Raspberry Pi/ARM in 2024, so old tool references are not the current target.

### Assignments and feedback

[Assignments](https://cs107e.github.io/assignments/) begins with Assignment 0 setup, then Larson Scanner, Clock, String Formatting, Stack and Heap, Keyboard and Simple Shell, Graphics Library and Console, and System Monitor with Interrupts. A2–A7 continually extend the same library, so skipping an early assignment breaks later interfaces. Historical guidance estimates roughly 10–20 hours each week.

When a layer is added, rerun the checks below it: logic traces for GPIO and
timers; host-side/unit tests for formatting and allocation; raw scan codes and
parser cases for keyboard and shell; pixel coordinates and boundary images for
the framebuffer; interrupt counts, latency, and a shared-state invariant for
the monitor. When memory corruption appears, reduce it to a small triggering
program and draw the address map; the final display cannot explain a low-level
fault.

The course organization maintains
[xfel](https://github.com/cs107e/xfel), an MIT-licensed fork of the tool used
for current D1 bring-up. Its README exposes memory read/write, hexdump,
execute, and JTAG operations. This is tooling, not an assignment
implementation. For Assignment 0, read the chip version, read back from a
known-safe address, and compare the image checksum; do not write to unknown
flash regions.

[Labs](https://cs107e.github.io/labs/) lists Lab 0–9, progressing from the
board and execution below C through debugging, linking, keyboard input, the
framebuffer, and interrupts, with 2 project meetings. Pair every driver with a
minimal test and observe it through UART logs or GPIO traces. A black screen
alone cannot distinguish a linker script, clock, pin protocol, or
memory-corruption failure.

The defining interface is the runtime you construct. Mark text/data/bss/heap/stack boundaries in the linker script, define allocation alignment and exhaustion behavior, and document context save/restore and reentrancy limits in interrupt handlers. For each peripheral, retain a small polling baseline before moving to interrupt-driven operation; their comparison separates protocol faults from concurrency faults.

### Final project

The [Project](https://cs107e.github.io/project/) is normally built by 2 people
in 2–3 weeks. Its proposal defines core, stretch, and fallback scopes, budget,
ownership, and risk milestones. A solo public rebuild can keep the same
structure while reusing its own allocator, console, interrupts, and drivers;
switching to an off-the-shelf OS would cut the first 7 weeks out of the system.
Put the BOM, interface diagram, build commands, failure log, live or recorded
demo, and a README explaining the hardest tradeoff in the project directory.

### Access and version notes

Spring 2026 meets for 2 lectures of 90 minutes and 1 lab of 2 hours each week, with no recordings or remote section and a cap of 40. The [Stanford FAQ](https://web.stanford.edu/class/cs107e/) lists the 2025–26 kit at 75 dollars and says the SBC is returned at term end. Visitors can read the [Schedule](https://cs107e.github.io/schedule/) and public writeups, but not the student repository, reference implementation, Ed, or staff check-ins.

Test the public toolchain and confirm that you can obtain a Mango Pi before
buying hardware. The point of CS107E is not peripheral count, but whether
machine code, the runtime, allocator, drivers, and an interrupt-driven console
join along one boot path. Isolated peripheral demos do not show a system
growing layer by layer.

The most revealing demonstration begins from power-off: build the image, boot,
run diagnostic commands through UART or the console, and trigger one
recoverable error. Diagram the boot path, memory map, driver dependencies, and
project reuse in the README. If recovery still runs through the runtime and
interrupt library you wrote, the project genuinely continues the A2–A7 line.
