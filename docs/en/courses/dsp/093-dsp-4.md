### Access and version notes

[The current EPFL DSP 4 page](https://www.coursera.org/learn/dsp4) lists
3 modules, 2 graded assignments, and 4 ungraded labs spanning image processing, digital
communications/ADSL, and real-time audio. It fits learners who already know
convolution, the DFT, filtering, and sampling and want to see those tools
constrained by rate, distortion, BER, and deadlines. Choose only the first
part for image compression; the real-time route also assumes C/C++, buffers,
and digital-audio interfaces.

### Labs and projects

The four official ungraded labs are Haar Bases for Image Compression, The
Telephone Channel, Simple Data Transmission, and Voice Transformers. The
three-part portfolio below combines the two communications labs. This is an
**unofficial self-study grouping**, separate from Coursera's 2 graded
assignments and platform grading structure.

For the image part, report the coefficient rule, compression ratio, and
reconstruction error, then explain a texture or edge failure. The
communications part connects the telephone-channel model to the
simple-transmission modem and states sampling rate, symbol rate, channel/noise
model, and BER. For real-time audio, validate Voice Transformers offline
before measuring block execution time, buffer deadline, and dropped blocks.
Without a board, stop at the offline reproduction. A shared
representation–algorithm–implementation table is useful, but the
metrics remain different: rate–distortion for images, bandwidth–BER for
communications, and perceptual effect plus deadline for real-time audio.

### Code Sources and Hardware Limits

Old [DSPNumex](https://github.com/LCAV/DSPNumex)
[NumEx8](https://github.com/LCAV/DSPNumex/tree/master/NumEx8) supplements only
image processing. Real-time work has the official
[mooc-hwlab](https://github.com/LCAV/mooc-hwlab) and
[online tutorial](https://hwlab.learndsp.org/) covering Nucleo,
STM32CubeIDE, and audio passthrough; check the
[bill of materials](https://hwlab.learndsp.org/bill-of-materials) and board
revision before buying. Public files do not include the Coursera grader,
instructor feedback, or certificate, and old IDE/API details may require a
minimal compatibility patch. Note the commit, tool version, wiring, baseline,
and worst-case execution time beside the hardware result. Start the hardware route with stable, effect-free
audio passthrough, then add processing block by block until underrun, clipping,
or a missed deadline first appears. An offline route should use the same frame
length and sampling rate. That comparison shows how the platform constrains the
algorithm; a sound clip that happens to play establishes only a successful
input.

In the real-time branch, the decisive question is which block first exhausts
the deadline, buffer, or dynamic range and how the algorithm yields to that
limit. The useful choice is concrete: shorten the filter, shrink the frame, or
trade a little perceptual quality for stable passthrough. Sound merely emerging
does not answer it.
